# Skills

The skill contract: how a skill is declared, invoked and answers, how the catalog the model sees is generated, the stub backend and fault injection, and how to add a skill. Robot-side behaviour (SDK calls, real backend, posture rule, settle waits) is in [robot.md](robot.md).

A skill has two parts:

1. `skills/catalog/<name>/SKILL.md`: YAML frontmatter that the registry reads, plus a short model-facing body in a fixed section template ([below](#skillmd-body)). This file is the skill's **manifest**: frontmatter plus body sections. Nothing in a `SKILL.md` is for humans; human documentation lives in this page and [robot.md](robot.md).
2. `skills/<name>.py`: a module with a `main()` that runs as a subprocess, and a module-level `POLICY` object that the dispatcher reads.

v1 skills: `walk`, `turn`, `sit`, `stretch`, `detect_object`. Two utilities, `stop_move` and `read_state`, run the same way but are not skills: they have no `SKILL.md` and the model never sees them. Two long-running services support the skills: the [robot service](#robot-service), which every skill reads robot state through and which runs every motion for them, and the [vision service](#vision-service), which `detect_object` asks. The registry loads every subfolder of `skills.dir` that has a `SKILL.md`, so a different skill set (for example another granularity tier) is a different folder ([running.md](../../docs/running.md)).

## SKILL.md frontmatter

The YAML block between the first two lines that are exactly `---` (the file must start with `---`), parsed with `yaml.safe_load`. The schema (`ParamSpec`, `SkillFrontmatter`, `SkillSection`, `SkillFile`) and the parser (`parse_skill_file`) live in `skills/manifest.py`; the dispatcher's registry calls them and adds the checks that need the folder or the module. `parse_skill_file` validates the frontmatter, then the [body](#skillmd-body), and returns a `SkillFile`: the `SkillFrontmatter` keys plus `sections`.

| Key | Type | Required | Meaning |
|---|---|---|---|
| `name` | string matching `^[a-z][a-z0-9_]*$` | yes | Must equal the folder name and `POLICY.name`; this also makes names unique, so there is no separate duplicate check. |
| `entrypoint` | string | yes | Module run with `python -m`, for example `skills.walk`. |
| `description` | one-line string | yes | Shown in the catalog. |
| `params` | mapping name → ParamSpec | no | Parameters, in catalog order. Absent means no parameters. |
| `expect` | any | no | Reserved for v2 verification. Accepted and ignored. |

ParamSpec (parameter names match `^[a-z][a-z0-9_]*$`):

| Key | Type | Applies to | Meaning |
|---|---|---|---|
| `type` | `number` \| `string` \| `enum` | all | Required. |
| `description` | non-empty string | all | Required. Short. |
| `values` | non-empty list of unique lowercase strings | `enum` | Required for `enum`, not allowed otherwise. |
| `min`, `max` | finite number | `number` | Optional, inclusive, `min <= max`. |
| `default` | value of the param's type | all | Optional. If absent, the parameter is required. Must pass the param's own checks. |
| `unit` | non-empty string | `number` | Optional. Shown in the catalog. |

Any other key (`sections` included), a missing required key or an invalid value is a registry error, as is a body that breaks the [template](#skillmd-body), and so are: an entrypoint that cannot be imported, a module without `POLICY`, a `POLICY` that is not a `SkillPolicy`, `POLICY.name` ≠ `name`, a missing skills folder, or zero skills. Transports print `Registry error: <message naming the file>` and exit 2. A frontmatter error reads `<path>: <dotted.loc>: <msg>` (e.g. `params.distance_m.min`); an extra key reads `unknown key`; a body error reads `<path>: body: <msg>`. The parser raises these as `SkillFileError`, and the registry re-raises them unchanged as registry errors.

`skills/catalog/walk/SKILL.md` is a full example. The dispatcher checks every planned step against these declarations before anything runs ([loop-and-context.md](../../dispatcher/docs/loop-and-context.md#step-bounds)).

## SKILL.md body

Everything after the closing `---` is the body: text for the model, written for the planner. It holds only what the planner needs to choose calls and params: preconditions (such as failing while sitting), effects and limits (such as speed or the COCO-class restriction). No SDK calls, rates, environment variables, settle constants or run commands; those are here and in [robot.md](robot.md). Params, ranges and the one-line `description` are already in the frontmatter and are not repeated.

The body is exactly these sections, each a line `## <heading>` followed by its text, in this order (`SECTION_HEADINGS`):

| Heading | Says |
|---|---|
| `Use when` | When the planner should pick this skill. |
| `Requires` | Preconditions; a call that breaks one fails. |
| `Effect` | What changes on success, including speeds. |
| `Limits` | What the skill cannot do or guarantee. |

Every section is required. When nothing applies, its text is `None.`. Blank lines are allowed anywhere. `parse_skill_file` rejects, with `<path>: body: <msg>`:

- a missing section (`missing section '## Requires'`, naming the first missing one);
- any other heading line (a line starting with 1 to 6 `#` and a space), including `# <name>` titles and `###` subheadings (`unknown heading`);
- a repeated or out-of-order section;
- a non-blank line before the first heading (`text outside a section`);
- an empty section;
- a body longer than `BODY_MAX_CHARS` = 800 characters after stripping (tunable), headings included.

`SkillFile.sections` is a tuple of frozen `SkillSection(heading, text)`, one per heading in template order: `heading` without the `## ` prefix, `text` stripped of surrounding whitespace and otherwise verbatim (inner line breaks kept). The dispatcher renders them without knowing the heading names.

Numbers in the body that mirror a code constant are literal: walk's `0.3 m/s` is `VELOCITY_MPS` and turn's `1.0 rad/s` is `YAW_RATE_RPS`. `test_prose_numbers_match_code_constants` in `skills/tests/unit/test_manifest.py` fails if a body and its constant disagree; a new mirrored number gets a line there.

## Catalog and registry hash

The catalog (`Registry.catalog_text()`) is generated from the frontmatter and the body sections, skills sorted by name, one line per parameter, no trailing newline. The body sections are sent to the model in full, rendered after the parameter lines ([loop-and-context.md](../../dispatcher/docs/loop-and-context.md) has the format). The catalog is sent as `system[1]` = `"## Skills\n" + catalog`. The current catalog is the golden file `dispatcher/tests/golden/catalog.txt`.

Type phrases: `one of a, b`; `text`; `number from X to Y`, `number, at least X`, `number, at most Y` or `number`, followed by the unit.

The **registry hash** is the first 16 hex characters of SHA-256 over `system_text + "\n" + catalog_text + "\n" + json.dumps(tool_schema, sort_keys=True)`. It identifies the whole prompt surface, so it changes with the skill set, any `SKILL.md` frontmatter and body wording, the system text and the horizon (which appears in the system text and the tool schema). It is logged in `task_start` and `index.jsonl`; runs with different hashes are not directly comparable. `go2 catalog` prints the system text, catalog, tool schema and hash.

## Invocation

```
python -m skills.<name> '<params-json>'
```

- `argv[1]` is a JSON object with the **filled** params: checked, normalised and with defaults filled in by the dispatcher. Always present (`{}` for no params).
- Environment, set by the executor through `skills.env.child_env()` (secrets `ANTHROPIC_API_KEY` and `TELEGRAM_BOT_TOKEN` removed by the executor first). `skills/env.py` defines every variable name below; skills and backends read them only through its constants:

| Variable | Meaning |
|---|---|
| `GO2_BACKEND` | `real` or `stub`. Missing or unknown → `backend_not_configured`. |
| `GO2_IFACE` | Network interface (real backend). |
| `GO2_YOLO_WEIGHTS` | Path to the YOLO weights. |
| `GO2_STUB_STATE_FILE` | Stub state file. |
| `GO2_STUB_TIME_SCALE` | Stub time scale. |
| `GO2_STUB_OBJECTS` | JSON `{class: {"x": m, "y": m, "height_m": m}}`, the objects in the stub world ([stub backend](#stub-backend)). |
| `GO2_STUB_FAULT` | Fault kind; set only for the faulted step, never inherited from the dispatcher's environment. |
| `GO2_PARENT_PID` | Dispatcher PID, for the orphan watchdog. |
| `GO2_VISION_SOCKET` | Unix socket of the [vision service](#vision-service); `child_env` sets it to `env.vision_socket_path(parent_pid)`. Read by `detect_object` and the service. |
| `GO2_ROBOT_SOCKET` | Unix socket of the [robot service](#robot-service); `child_env` sets it to `env.robot_socket_path(log_dir)` = `<log_dir>/robot.sock`. Read by every skill and by the service. |
| `GO2_LEASE_TOKEN` | The step's [lease](#lease) token, which the dispatcher armed on its control connection before the step; `child_env(..., lease_token=)` sets it for that step only, never inherited. A motion skill sends it with every primitive; without it the service rejects motion (`motion_rejected`). |
| `PYTHONUNBUFFERED` | `1`. |

- The process runs with the base dir as working directory, in its own session (`start_new_session=True`), so a kill reaches the whole process group ([safety.md](../../docs/safety.md#the-stop-path)).
- **Output:** exactly one JSON line on the real stdout, written by `runner.emit()` through the stdout fd that `skills/process.py` saves. Everything else goes to stderr: `process.capture_stdout()` points fd 1 at stderr first, so output from the SDK, CycloneDDS, ultralytics or C code cannot corrupt the response line. The executor reads the last non-empty stdout line and requires its `skill` to match.
- **Exit code:** 0 for `status = "ok"`, 1 for `status = "error"` (`emit` uses `os._exit`, because DDS threads can hang normal interpreter shutdown). No valid response line means step outcome `malformed`.
- Skills do not validate params: they read them directly (`params["direction"]`) and apply no defaults. The dispatcher validates every plan against the `SKILL.md` types, enums and ranges before it runs a skill ([loop-and-context.md](../../dispatcher/docs/loop-and-context.md#step-bounds)). A skill run by hand is therefore not range-limited and needs all params; a missing key or wrong type ends as `exception`. Only `detect_object.target` is trimmed and lower-cased by the skill.

## Response schema

Every skill and utility prints one `SkillResponse` (`schema_version` 2). `SkillResponse`, `SkillError` and `RobotState` are defined once, as frozen standard-library dataclasses in `skills/schema.py`; the dispatcher re-exports them from `dispatcher/models.py`. The response is built by `runner.build_response(skill, outcome, states, total_ms, *, setup)` (`skills/runner.py`) from its four sources and printed with `runner.to_json` (`json.dumps(dataclasses.asdict(...), allow_nan=False)`):

- `outcome`, the frozen `SkillOutcome` the body returns: `status`, `observations`, `error`, and the body's own timing keys. An exception that escapes the body becomes `SkillOutcome.from_exception(e)`: `InvalidParams` maps to `invalid_params`, `BackendNotConfigured` to `backend_not_configured`, anything else to `exception` with message `<ExceptionType>: <first line>` (`runner.describe_exception`) and its traceback on stderr.
- `states`, the `runner.StateSampler` that `run_main` creates before the body runs: `state_before`, `state_after`, `state_error` (the failed samples' `<label>: <ExceptionType>: <first line>`, joined with `; `) and the time spent sampling. `states.take("before" | "after")` samples into that field; `strict=True` re-raises a failed sample instead of recording it. `BackendNotConfigured` always propagates. Because `run_main` owns the sampler, a sample taken before an exception is still reported. By default (skills) the sampler reads through the [robot service](#robot-service) on the process's one connection, `robot_ipc.session`, connecting before the timed read. The utilities pass their own `reader` and `prepare` (`skills/local.py`): a read in the process itself, which on the real backend means its own DDS subscription, after DDS init ([robot.md](robot.md#state-sampling)).
- `total_ms`, measured by `run_main` from its start to `emit`.
- `setup`, the process's setup time, read by `emit` from `run_main`'s `setup` callable: in a skill `robot_ipc.session.setup_timing()`, `{"robot_connect_ms": ...}` once the process has connected to the robot service; in a utility `local.setup_timing()`, `{"dds_init_ms": ...}` once it has attempted DDS init ([robot.md](robot.md#sdk-and-dds-usage)). Empty when the process did not get that far.

`timing` is the setup key, then the outcome's keys, then `state_ms` if a sample was attempted, then `total_ms`. `run_main(skill, body, *, watchdog=True, states=None, setup=robot_ipc.session.setup_timing)` runs `body(states)` and emits; `run_skill(policy, body, *, sample_state=True)` wraps it for skills (parse params, sample before, `body(params)`, sample after). The utilities pass their own body, sampler and setup to `run_main`: `stop_move` returns its `invalid_params` error after `StopMove()` so `sdk_ret` and its timing are kept, and `read_state` samples strictly and maps a failure to `state_unavailable`. Neither needs the robot service: `stop_move` must work when nothing else does, and `read_state` is the diagnosis read that bypasses the service.

Constructing a `SkillResponse` checks only that `error` is present if and only if `status = "error"`. `build_response` also raises `ValueError` for `status = "error"` without `error_code` or `error_message`; `emit` turns any exception while building or serialising the line into an `exception` error line without the body's observations and states. The dispatcher validates the whole line against the same classes with a pydantic `TypeAdapter`: types, enums, and no unknown keys at any level, including inside `error` and the state objects. A line that fails it is step outcome `malformed`.

| Field | Meaning |
|---|---|
| `schema_version` | Always `2`. |
| `skill` | Skill name; must match the skill that was run. |
| `status` | `ok` or `error`. |
| `observations` | Skill-specific results. |
| `error` | `{code, message}` if and only if `status = "error"`, else `null`. `message` is collapsed to one line (whitespace runs become one space) and not length-limited; the dispatcher cuts it where it shows it ([loop-and-context.md](../../dispatcher/docs/loop-and-context.md#user-message)). |
| `state_before`, `state_after` | Robot state sampled at start and end ([robot.md](robot.md#state-sampling)), each with the `seq` of the message it was read from and its `age_ms` at the read; utilities have `state_after` only. |
| `state_error` | Why a state sample failed (`before: ...` / `after: ...`, joined with `; `), else `null`. |
| `timing` | Milliseconds, each part measured once. `robot_connect_ms` (skills): the connect and `hello` to the robot service, summed over the process's connects. `dds_init_ms` (utilities): DDS init, once per process. `client_init_ms` (`stop_move`): sport client creation and `Init()`, DDS init excluded. `connect_ms`: `detect_object`'s connect to the vision service. `exec_ms`: the skill's action; for `walk` and `turn` the `move` request until its reply, for `sit` and `stretch` the `action` request plus the settle wait. `stop_call_ms` (`stop_move`): the `StopMove()` call until it returns. `state_ms`: time in the state samples, connect and DDS init excluded; in a skill, the round trips to the robot service; in a utility, its own read. `total_ms`: the whole process from `run_main` start. The setup key is present only if the process got to that setup, `state_ms` only if a state sample was attempted (both absent, for example, when a skill's params are invalid). |

**Reading records without `dds_init_ms`.** Run logs whose timing has no `dds_init_ms` key used other timing meanings: `init_ms` is the sport client creation and `Init()` (`client_init_ms`), or the vision connect in `detect_object` (`connect_ms`); `state_ms` includes DDS init, which ran inside the first state sample; and `stop_call_ms` runs from utility start to the return of `StopMove()`, so it includes DDS init and client creation. Compare such records with current ones only by these definitions.

**Reading skill records with `client_init_ms`.** A skill whose timing has `client_init_ms` created its own DDS participant and sport client and sent `Move` itself: its timing has `dds_init_ms` and `client_init_ms` instead of `robot_connect_ms`, and its `state_ms` includes the robot service connect. Compare such records with current ones only by these definitions.

**Reading records with `schema_version` 1.** Skills read state in their own process with their own DDS subscription: a skill's `state_ms` includes the subscription, DDS discovery and the wait for the first message (DDS init is in `dds_init_ms` when present), and every skill, `detect_object` included, reports `dds_init_ms`. The states have no `seq` and `age_ms`.

Robot state fields, their sources and the posture rule are in [robot.md](robot.md#state-sampling). State is **logged only**; the model sees only the derived posture ([loop-and-context.md](../../dispatcher/docs/loop-and-context.md#user-message)).

Run a skill by hand ([below](#running-a-skill-by-hand)) to see a full response.

## The skills

| Skill | Action | Observations | Shown to the model on `ok` |
|---|---|---|---|
| `walk` | `move` primitive: `Move` for `distance_m / VELOCITY_MPS + LEAD_S` s, then `StopMove` | `direction`, `distance_m`, `duration_s` (commanded), `sdk_ret` | nothing |
| `turn` | `move` primitive with a yaw target: `Move(0, 0, ±YAW_RATE_RPS)` until the measured yaw change reaches the angle, capped at `radians(angle_deg) / YAW_RATE_RPS × CAP_FACTOR + CAP_S` s, then `StopMove` | `direction`, `angle_deg`, `duration_s`, `sdk_ret`, `closed_loop`, `turned_deg` | `closed_loop`, `turned_deg` |
| `sit` | `action` primitive `StandDown`, then a settle wait | `sdk_ret` | nothing |
| `stretch` | `action` primitive `Stretch`, then a settle wait | `sdk_ret` | nothing |
| `detect_object` | asks the [vision service](#vision-service) for one camera frame + YOLO; never moves | `target`, `object_found`, `position` (left/center/right), `closeness` (near/medium/far), `confidence` | `object_found`, `position`, `closeness`, `confidence` |

The skills keep the motion policy (speeds, lead times, direction maps, durations) and send it to the [robot service](#robot-service) as one primitive; the service runs it. Params and ranges are in each `SKILL.md`. Walk is open loop; turn stops on the measured yaw and falls back to open loop when no fresh yaw is readable ([robot.md](robot.md#motion)); walk's `left` and `right` are sideways steps that keep the heading. `walk`, `turn` and `stretch` need the robot standing: while sitting, `Move` and `Stretch` return non-zero and the skill reports `sdk_error` (stub behaviour, [below](#stub-backend); *unverified* on the robot). `sit` while already sitting is `ok`. `detect_object` reports the most confident box of the target class; the target must be one of the 80 COCO classes in `skills/coco.py`. Not finding an object is `status = ok` with `object_found: false`, not an error.

### Error codes

The codes are the members of `ErrorCode` in `skills/schema.py`, a `str` enum: skills pass members, the response line carries the plain string, and `SkillError.code` stays a `str`.

| Code | Skills | Meaning |
|---|---|---|
| `invalid_params` | all | The params argument is missing, not valid JSON, or not a JSON object. Keys and values are not checked by the skill (the dispatcher validates them). |
| `sdk_error` | walk, turn, sit, stretch, stop_move | An SDK call returned non-zero. Message `<Call> returned <code>` (walk/turn add `; StopMove returned <code>` if the cleanup stop also failed). The service sends `StopMove` after a failed `Move`. Whether the robot is left moving is not read from this code: the service ends the lease with another `StopMove`, and the `disarm` reply reports the lease's latest one if it failed ([Lease](#lease)). |
| `robot_unavailable` | walk, turn, sit, stretch | The [robot service](#robot-service) could not be used for the primitive: `ServiceUnavailable: <message>` (nothing listening, connection lost, no reply in time, malformed reply). |
| `motion_rejected` | walk, turn, sit, stretch | The service refused the primitive or ended it: `no_lease: <message>` (no lease armed, wrong or missing `GO2_LEASE_TOKEN`, another connection holds the lease, deadline passed) or `aborted: the lease ended: <reason>` (stop, disarm, re-arm or deadline while it ran; the robot was stopped). |
| `backend_not_configured` | all | `GO2_BACKEND` missing or unknown, or `GO2_IFACE` empty on the real backend. |
| `exception` | all | Unexpected exception: `<Type>: <first line>`. The traceback goes to stderr. Also the robot service's `sdk_exception`, when its sport client raised (it then sent `StopMove`). |
| `unsupported_object` | detect_object | Target is not one of the 80 COCO classes, for example `'phone' is not a detectable object. Closest supported: cell phone, spoon, horse.` (up to 3 close matches, if any). |
| `detector_error` | detect_object | Any other detector failure (`backend.DetectorError`; the specific cases below are its subclasses). |
| `camera_unavailable` | detect_object | The camera returned an error or no data (also the stub's `error` fault). |
| `vision_unavailable` | detect_object | The [vision service](#vision-service) could not be used: `GO2_VISION_SOCKET` unset, nothing listening (`no vision service at <path>: <error>`), the connection lost, no reply within `REPLY_WAIT_S` (`no reply within 5s`), or a malformed reply. |
| `bad_frame` | detect_object | The image could not be decoded. |
| `weights_missing` | detect_object | The YOLO weights file does not exist. |
| `state_unavailable` | read_state | No state could be sampled. |

Detector errors have the message `<ExceptionType>: <message>`; an error the service raised keeps the message the service built, in the same form. Outcomes the dispatcher adds on its own (`timeout`, `malformed`, `rejected`, `motion_budget_exceeded`, `interrupted`) are listed in [loop-and-context.md](../../dispatcher/docs/loop-and-context.md#step-outcomes).

## Policies

Each skill module defines one module-level `POLICY = policy.SkillPolicy(name, timeout, cost, context_observations)` (`skills/policy.py`). `timeout` and `cost` (a `MotionCost(distance_m, rotation_deg)`, default zero) are each a constant or a function of params; `context_observations` lists the observation keys shown to the model on `ok`. The dispatcher imports the module only to read `POLICY`.

The dispatcher reads only `name`, `context_observations`, `timeout_s(params)` and `motion_cost(params)`, with the filled, checked params. Every number is a module-level constant in `skills/<skill>.py`, except the motion timeout rule, which `walk` and `turn` share from `skills/motion.py`:

| Skill | Timeout | Motion cost |
|---|---|---|
| `walk` | `motion_timeout(distance_m / VELOCITY_MPS + LEAD_S)` | `distance_m` |
| `turn` | `motion_timeout(radians(angle_deg) / YAW_RATE_RPS × CAP_FACTOR + CAP_S)` (the cap) | `rotation_deg = angle_deg` (requested, not measured) |
| `sit`, `stretch`, `detect_object` | `TIMEOUT_S` | zero |

`motion.motion_timeout(motion_s)` is `MOTION_BASE_S + MOTION_FACTOR × motion_s` (10.0 s and 1.5): `MOTION_BASE_S = PROCESS_OVERHEAD_S + SPORT_CLIENT_TIMEOUT_S`, where `PROCESS_OVERHEAD_S` (5.0 s, tunable) covers process start, the robot service connect and the two state samples, and `SPORT_CLIENT_TIMEOUT_S` (5.0 s, tunable, `skills/robot_ipc.py`) is one lost `StopMove` reply in the service; `MOTION_FACTOR` (tunable) is a margin on the commanded motion time `motion_s`. Each of `walk` and `turn` computes `motion_s` in one private `_motion_s(params)`, used by both its timeout and its body, and asks for it with `motion.move(Velocity(vx, vy, vyaw), duration_s, target=None)` (turn passes a `MoveTarget`, and `motion_s` is its cap), which the service runs at `robot_ipc.CMD_PERIOD_S` (0.1 s, 10 Hz); `detect_object`'s `TIMEOUT_S` is `PROCESS_OVERHEAD_S + REPLY_WAIT_S` (10.0 s), where `REPLY_WAIT_S` (5.0 s, tunable) is its wait for the vision service's reply: one camera frame (`CAMERA_TIMEOUT_S`, 3.0 s) plus inference on a detector the service has already loaded, so a service that does not answer ends the call as `vision_unavailable` before the dispatcher kills it. The timeout covers the whole process from start to exit, including any [settle wait](robot.md#settle-waits). Every process whose call reaches the sport client (`walk`, `turn`, `sit`, `stretch` through the service, `stop_move` directly) has a timeout of at least `PROCESS_OVERHEAD_S + SPORT_CLIENT_TIMEOUT_S` plus its motion or settle time at max params. Each primitive makes at most one reply-waiting call (`StopMove`, `StandDown` or `Stretch`; `Move` sends without a reply), and a skill waits for the primitive's reply for its duration plus `SPORT_CLIENT_TIMEOUT_S` plus `REPLY_WAIT_S` (2.0 s), so a service that does not answer ends the call as `robot_unavailable` before the dispatcher kills it. `tests/integration/test_skill_policies.py` enforces this. The motion cost feeds the motion budget ([safety.md](../../docs/safety.md#motion-budget)).

The utilities `stop_move` and `read_state` export a `POLICY` too, so every module the dispatcher runs carries its name and timeout the same way: `SkillPolicy(name, timeout=TIMEOUT_S)` with `TIMEOUT_S` 12.0 s for `stop_move` (one lost `StopMove` reply plus its settle wait, tunable) and 10.0 s for `read_state`, zero motion cost and no `context_observations` (the defaults). They have no `SKILL.md`, so the registry never loads them; their `POLICY` is never in the catalog or the registry hash.

## No side effects on import

Importing a skill module must do nothing: no SDK import, no DDS init, no argument parsing, no output. All work happens in `main()`, under `if __name__ == "__main__": main()`. At top level a skill imports only the standard library and `skills`. Third-party imports happen inside functions: `unitree_sdk2py` in `skills/real.py`, and `cv2`, `ultralytics` and `numpy` only in `skills/real_detector.py`, which only the [vision service](#vision-service) imports, so no skill process loads torch. A test imports every `skills` module in a fresh interpreter and checks that none of these were loaded. This is what lets the dispatcher read policies without touching the SDK. Skill processes never touch DDS at all: the contract "Skill processes never touch DDS" forbids the skill modules, `motion` and `runner` from importing `skills.real`, `skills.local`, `skills.robot_service`, `unitree_sdk2py` or `cyclonedds`, directly or indirectly. `skills` never imports `dispatcher`, pydantic or PyYAML, directly or indirectly; the one exception is `skills/manifest.py`, which imports pydantic and PyYAML at top level and is imported only by the dispatcher and the skill tests, never by a skill.

The import-linter contracts enforce these rules before every commit and in CI for every import chain through the repo's own modules, including imports inside functions ([testing.md](../../tests/docs/testing.md#import-boundaries)). They treat third-party packages as leaves, so a third-party import that pulls in pydantic or PyYAML (`import anthropic`, at top level or inside a function) passes them, and the fresh-interpreter test checks only the modules it lists; code review is what enforces the import rule above for such imports. That gap is accepted because the rule exists to keep skill spawn time low and already forbids the import.

## Stub backend

The stub (`skills/stub.py`) replaces only the robot: its sport client is `stub.SimRobot`, which the [robot service](#robot-service) runs as its one sport client on the sim backend (and `stop_move` creates in its own process), so processes, the lease, timeouts, kills and both stop paths run for real. It simulates only what the real backend gets from the robot (motion, the camera image, the state message) and reuses the rest, such as the detector's box classification. Constants are in `skills/stub.py`.

It keeps posture, an odometry pose and the running velocity command in one JSON state file, `{"posture": "standing" | "sitting", "pose": {"x": m, "y": m, "yaw": rad}, "command": [vx, vy, vyaw] | null}`. The pose is in the world frame: the robot starts at (0, 0) facing +x, and yaw is counter-clockwise. A missing file means standing at the origin; a missing `pose` means the origin and a missing `command` none. Every writer reads the file, changes its own fields and replaces the file atomically (temp file + `os.replace`). The writers are the service's `SimRobot`, whose lock serialises its threads (the motion loop and a `stop` from a handler thread), `stop_move`'s own `SimRobot`, and `stub.reset`; no cross-process lock is needed because `stop_move` and `reset` run only while the service is idle, stopped, hung or dead.

| Call | While standing | While sitting |
|---|---|---|
| `Move` | 0 | 1 (not standing) |
| `StopMove` | 0 | 0 |
| `StandDown` | 0; posture → sitting, command cleared; waits `STAND_DOWN_S` | 0; no change |
| `Stretch` | 0; waits `STRETCH_S` | 1 |

- **Odometry.** An accepted `Move(vx, vy, vyaw)` (return 0) stores the command in the state file and `StopMove()` clears it, so a command stays set until a `StopMove` arrives, as assumed for the robot ([robot.md](robot.md#working-assumptions)). The service's motion clock is `SimRobot.wait(seconds, abort)`: it waits the scaled time or until the primitive is aborted, and while a command is stored advances the pose by the **unscaled** seconds waited, integrating the body-frame velocity exactly along the arc. The pose moves only while the service's motion loop waits; a command left set by a dead or hung service shows in `velocity` but moves no pose. Body frame as on the Go2: +vx forward, +vy left, +vyaw counter-clockwise (left). The stub does not model the start ramp or the coast, so walk overshoots on the stub by its lead time, and turn stops at the first command period whose yaw change reaches the angle minus `YAW_STOP_MARGIN_RAD`: between 3° short and 0.1 rad (5.7°) minus 3° past at `YAW_RATE_RPS` (`turn 90°` stops after 16 periods at 91.7°), where the robot stops about the margin short and then coasts ([robot.md](robot.md#motion)). The sim backend's service publishes a state after every motion-clock wait as well as every `SIM_PERIOD_S`, so a yaw target reads the pose of the tick just run at any time scale.
- **Camera.** `StubDetector`, served by the [vision service](#vision-service) with the service's own env: `detect(target)` waits `DETECT_S`, then projects the object listed under `target` in `GO2_STUB_OBJECTS` through a pinhole camera `CAMERA_OFFSET_M` ahead of the body centre (`CAMERA_WIDTH_PX` × `CAMERA_HEIGHT_PX`, horizontal field of view `CAMERA_HFOV_DEG`, square pixels; [robot.md](robot.md#object-detection)). The box centre-x fraction is `0.5 − f × tan(bearing) / width`, so a positive bearing (left) gives a small x; the box height fraction is `f × height_m / depth / height`, clipped to 1, where depth is the distance along the camera axis. The box goes to the real detector's classifier, `vision.classify_box`. Not found when the target is not listed, is behind the camera, is outside the horizontal field of view, or its box height fraction is below `MIN_BOX_H`. Confidence is deterministic: `CONFIDENCE_MIN` + (`CONFIDENCE_MAX` − `CONFIDENCE_MIN`) × box height fraction.
- **Objects.** `GO2_STUB_OBJECTS` is a JSON object: each key is a COCO class name and each value is `{"x": number, "y": number}` in metres in the world frame, with an optional `"height_m": number > 0`; no other keys. Without `height_m` the class's entry in `DEFAULT_HEIGHTS_M` is used (bottle 0.25, cup 0.10, chair 0.90, person 1.70); a class without one is an error naming the class. `stub.parse_objects(data)` holds these rules and raises `ValueError`. One object per class.
- `sample_state()` is the stub's state message. Skills see it through the [robot service](#robot-service), whose sim source calls it every `SIM_PERIOD_S`; the utilities call it in their own process. It reports `body_height` per posture (`BODY_HEIGHT_*_M`), `position` = [x, y, `body_height`], `imu_rpy` = [0, 0, yaw], and `velocity` (world frame) and `yaw_speed` from the stored command, so zero at rest. `mode`, `gait_type`, `foot_force`, `error_code` and `range_obstacle_raw` are `null`. `obstacle_m` is ray-cast from the body centre in the body's front, back, left and right directions against the objects in `GO2_STUB_OBJECTS`, each a disc of radius `OBSTACLE_RADIUS_M` (0.15 m, *tunable*); the distance is to the disc's edge, and a direction with no hit within `OBSTACLE_MAX_M` (5 m, *tunable*) is `null`. Stub robots can walk through objects: with the body centre inside a disc, every direction reports 0.0. The real mapping never yields 0.0, because it treats 0 as unknown. The stub models no walls or room bounds, so an empty world gives all `null`. The stub invents no raw array, because the encoding the firmware uses is unknown ([robot.md](robot.md#state-sampling)).
- All stub waits are multiplied by `stub.time_scale`: skills wait through `backend.sleep()`, the service's motion loop through `SimRobot.wait`. Skills never call `time.sleep` themselves.
- The stub is reset to `stub.initial_posture` at the origin at startup and by `go2 --reset-stub`, not between tasks ([running.md](../../docs/running.md)). The dispatcher does this with `stub.reset(posture, path)`, its only access to stub state; start-up posture on either backend comes from the `read_state` utility.

### Fault injection

Faults exercise every failure path with real processes. They apply to the stub backend only (`stub.faults` must be empty with `robot.backend = "real"`; that is a config error).

Configure them in config:

```toml
[stub]
faults = [ { step = 2, kind = "hang" } ]
```

or on the command line with `--fault STEP:KIND` (repeatable), which replaces the whole list ([running.md](../../docs/running.md)).

- `step` counts **dispatched** steps in the task, 1-based, across plans. Rejected steps are not counted. Steps must be unique.
- The dispatcher sets `GO2_STUB_FAULT` for that step only. The skill process applies it at its first action call (`stub.inject_fault()`), before it asks a service: the `move` or `action` primitive, or `detect`. Later calls behave normally. `error`, `hang`, `crash` and `garbage` act in the skill process, so neither service sees them.
- The service faults `service_hang`, `service_crash` and `stop_error` are forwarded: the skill sends `"fault": kind` with its primitive, and the robot service applies it mid-primitive: after the first `Move` of a `move`, so the sim robot keeps a velocity command, or before the call of an `action`. `service_hang` and `service_crash` act on the whole process (`stub.apply_service_fault`); `stop_error` makes every `StopMove` the service sends fail with 99 (`stub.STUB_ERR_INJECTED`) without reaching the sim robot, until the next `arm`. The service accepts the field only on the sim backend and only with a service fault. `detect_object` ignores service faults.
- Utilities (`stop_move`, `read_state`) never read `GO2_STUB_FAULT`, so the fallback stop always works.
- The fault kinds are `stub.FaultKind` (`FAULT_KINDS`); the dispatcher's `stub.faults[].kind` config type is that same `Literal`, as `stub.initial_posture` is `stub.StubPosture`. The `stub.time_scale`, `stub.initial_posture` and `stub.state_file` config defaults are `stub.DEFAULT_TIME_SCALE`, `DEFAULT_POSTURE` and `DEFAULT_STATE_FILE`, the same values the stub uses when its env is unset.

| Kind | What the skill process does | Step outcome |
|---|---|---|
| `error` | the call returns 99 (`sdk_error`, e.g. `Move returned 99`); the detector raises a camera error (`camera_unavailable`) | `error` |
| `hang` | sleeps forever (not scaled) | `timeout` (killed, then `StopMove`) |
| `crash` | exits with code 139, no output | `malformed` |
| `garbage` | prints `not json` and exits 0 | `malformed` |
| `service_hang` | the robot service stops itself with `SIGSTOP` mid-walk: sockets stay open, nothing answers, the sim command stays set | `error` (`robot_unavailable`, no reply within the skill's reply wait) unless the dispatcher detects the hung service first (no `ping` or `stop_sent` reply) |
| `stop_error` | every `StopMove` of the robot service returns 99 until the next `arm`, the sim command stays set | `error` (`sdk_error`, `StopMove returned 99`, for `walk` and `turn`; `ok` for `sit` and `stretch`); the `disarm` reply carries `stop_failed` with `ret` 99 |
| `service_crash` | the robot service exits with code 139 mid-walk, the sim command stays set | `error` (`robot_unavailable`, connection lost); the dispatcher sees EOF on its control connection |

For one process run by hand, set `GO2_STUB_FAULT=<kind>` directly.

## Vision service

`detect_object` does not load a detector itself. It asks the vision service (`skills/vision_service.py`), a long-running process that loads the detector once, warms it up and answers requests on a Unix socket. On the real backend that is `RealDetector` (`skills/real_detector.py`: YOLO plus a `VideoClient` kept open across requests, [robot.md](robot.md#object-detection)); on the stub it is `StubDetector`, the simulated camera ([stub backend](#stub-backend)). The service only reads the camera: it never creates a `SportClient` and never commands motion. It grabs a frame only when a request arrives.

**Protocol** (`skills/vision_ipc.py`). `multiprocessing.connection` over the Unix socket at `GO2_VISION_SOCKET`, one request and one reply per connection, each a UTF-8 JSON object sent with `send_bytes` (never pickle), at most `MAX_MESSAGE_BYTES`:

- Request: `{"target": "<COCO class>"}`. The skill checks the target first; the service does not.
- Reply: the `DetectResult` fields `{"found": bool, "position", "closeness", "confidence"}` (the last three `null` when not found), or `{"error": {"code": "<error code>", "message": "<ExceptionType>: <message>"}}` with `camera_unavailable`, `bad_frame`, `weights_missing`, `backend_not_configured` or `detector_error`.

In `detect_object`, `connect_ms` is the connect and `exec_ms` the request until the reply. The service answers one connection at a time and drops a connection that sends no request within `REQUEST_WAIT_S` (1.0 s). If warm-up fails (weights missing, camera client not created), the service still becomes ready and logs the error to stderr; each request retries the part that failed and replies with its error code, so the model sees `weights_missing` rather than a dead service.

**Lifecycle contract** (owned by the dispatcher; the constants are in `skills/vision_service.py`):

- **Start:** `python -m skills.vision_service`, no arguments, working directory the base dir, environment `child_env(...)` with `fault` unset: the same call the executor makes for a skill, so `GO2_VISION_SOCKET` is `vision_socket_path(os.getpid())` = `<tempfile.gettempdir()>/go2-vision-<dispatcher pid>.sock` on both sides. Start it in its own session (`start_new_session=True`), with stdin `/dev/null`, stdout a pipe, and stderr (its log) to a file or inherited, never an unread pipe.
- **Ready:** the service writes exactly one line, `ready` (`READY_LINE`), to stdout once it is warmed up and listening; nothing else is ever written to stdout. Wait for it up to `STARTUP_TIMEOUT_S` (30.0 s, tunable). Exit before the line is a failed start; exit code 2 means `GO2_BACKEND` or `GO2_VISION_SOCKET` is missing or unknown.
- **Restart:** before each `detect_object` step, if the process has exited, start it again and wait for `ready`. A step whose service is down or slow is not retried: `detect_object` reports `vision_unavailable`.
- **Stop:** `SIGTERM`; it closes the listener, removes the socket file and exits 0. Send `SIGKILL` if it is still alive after `STOP_GRACE_S` (2.0 s).
- **Socket file:** created with mode `0600`. A file left by a killed service is removed by the next service at start.
- **Parent death:** the service runs the skills' orphan watchdog (`process.start_orphan_watchdog`, `GO2_PARENT_PID`): when its parent is gone it exits with code 137 within about 2.2 s, leaving the socket file for the next start to remove. Without `GO2_PARENT_PID` (a manual run) it runs until stopped.

## Robot service

Skills never touch DDS. The robot service (`skills/robot_service.py`) is a long-running process and the only long-lived DDS owner of the robot's sport state and motion. It holds the state source and **one sport client**, created at start and used for every motion primitive and every stop:

- **State.** On the real backend it subscribes to `rt/sportmodestate` once at start ([robot.md](robot.md#state-sampling)); on the sim backend (`GO2_BACKEND=stub`) its sim source puts `stub.sample_state()` into the same store every `SIM_PERIOD_S` (0.02 s, *tunable*). Either way a `state_store.StateStore` holds only the latest message, numbered `seq` from 1 and stamped `rx_mono` (`time.monotonic()`, CLOCK_MONOTONIC, comparable only on the same host) by the callback, which does nothing else; mapping to `RobotState` happens when a client reads.
- **Motion.** Real: one `SportClient` (`real.get_sport_client()`, after the state subscription's DDS init); sim: `stub.SimRobot` over the stub state file ([stub backend](#stub-backend)), so the stub runs the same process shape. Primitives run one at a time on the service's motion loop thread; a lease deadline thread and one handler thread per connection run beside it. One lock guards the lease and serialises every `Move` with the abort of its primitive, so no `Move` follows a stop. An action (`StandDown`, `Stretch`) waits for its SDK reply, so only its commit is under the lock: the abort check and taking the call, after which a stop no longer prevents it; the call itself runs outside the lock. If the lease ends during the call, the motion loop sends a trailing `StopMove` after the reply and the step is aborted, so `StopMove` is the last command either way. `StopMove` itself is sent from whichever thread ends the motion, outside the lock ([robot.md](robot.md#motion)).

**Protocol** (`skills/robot_ipc.py`, `PROTOCOL_VERSION` 1). `multiprocessing.connection` over the Unix socket at `GO2_ROBOT_SOCKET`, encoded as for the vision service (`skills/ipc.py`: UTF-8 JSON objects with `send_bytes`, never pickle), at most `MAX_MESSAGE_BYTES`. Connections are persistent: a client sends any number of requests on one connection, one at a time, and the service serves each connection on its own thread. Every message, both ways, is `{"v": 1, "op": ..., ...}`.

| Request | Connection | Reply |
|---|---|---|
| `{"op": "hello"}`, or `{"op": "hello", "role": "control"}` | any | `{"op": "hello", "backend": "real" \| "stub", "pid": int}` |
| `{"op": "state", "min_seq": int \| null, "wait_ms": number}` | any | `{"op": "state", "state": RobotState \| null, "rx_mono": number \| null, "link": "up" \| "down"}` |
| `{"op": "subscribe", "period_ms": number}` | any | `{"op": "subscribed", "period_ms": number, "link": ...}`, then the stream below |
| `{"op": "ping"}` | any | `{"op": "pong"}` |
| `{"op": "stop"}` | any | `{"op": "stop_sent", "ret": int \| null, "stop_call_ms": number}` |
| `{"op": "arm", "token": str, "timeout_s": number}` | control | `{"op": "armed", "token": str, "timeout_s": number}` |
| `{"op": "disarm"}` | control | `{"op": "disarmed", "stop_failed": {"reason": str, "ret": int \| null, "stop_call_ms": number} \| null}` |
| `{"op": "move", "token": str, "vx", "vy", "vyaw": number, "duration_s": number, "target"?: {"yaw_rad": number, "lead_s": number}, "fault"?: str}` | lease | `{"op": "move", "duration_s": number, "move_ret": int, "stop_ret": int \| null, "measured": {"yaw_rad": number \| null} \| null}` |
| `{"op": "action", "token": str, "name": "StandDown" \| "Stretch", "fault"?: str}` | lease | `{"op": "action", "ret": int}` |

- **`state`.** With `min_seq`, the service waits up to `wait_ms` (capped at `MAX_STATE_WAIT_S`, 5 s) for a message with `seq` ≥ `min_seq`; if none comes it answers with the latest earlier message. Without `min_seq` it answers at once. `state` is the `RobotState` mapped at the read, with `t` the read time, `seq` and `age_ms` (read time minus `rx_mono`); it is `null` while the service has had no message. `link` is `up` if the latest message is at most `state_store.LINK_GAP_S` (0.5 s, *tunable*) old, else `down`.
- **Stream.** After `subscribe` the connection only receives. Every `period_ms` (at least `MIN_STREAM_PERIOD_S`, 0.02 s) the service sends `{"op": "link", "link": ..., "rx_mono": ...}` if the link changed since the last check (`rx_mono` of the latest message then: for `down` the last one before the gap), then `{"op": "sample", ...}`, shaped like a `state` reply, if a message newer than the last one sent has arrived. A gap therefore shows as a `down` event, no samples, and an `up` event; its length is the next sample's `rx_mono` minus the `down` event's `rx_mono`, to within one period. The stream ends when the client closes the connection.
- **`stop`.** Ends any lease, aborts the running primitive and sends `StopMove` from the handler thread, whatever the state; the reply comes after `StopMove` returns. `ret` is its code (`null` if it raised) and `stop_call_ms` the call's time in the service. Accepted on any connection, so a stop never waits for a role.
- **`disarm`.** Ends the lease (`StopMove` if it was used), then waits until every `StopMove` the service has already decided to send has returned, whichever thread sends it, so a stop on the lease connection's EOF that is still running is included. `stop_failed` is the latest of those `StopMove`s since the `arm` if it failed (non-zero `ret`, or `ret` `null` if it raised), else `null`: `reason` is why the service sent it (for example `move done`, `lease deadline`, `lease connection closed`, `disarmed`) and `stop_call_ms` the call's time. A later `StopMove` that returns 0 clears it. A non-null `stop_failed` means the robot may still be moving.
- **`move`.** `Move(vx, vy, vyaw)` every `CMD_PERIOD_S` (0.1 s), `max(1, round(duration_s / CMD_PERIOD_S))` times, then `StopMove`. `duration_s` in the reply is the `Move`s sent × period; `move_ret` is the failing `Move`'s code (0 if none failed; the loop then stops at once and sends `StopMove`); `stop_ret` is the closing `StopMove`'s code. `vx`, `vy`, `vyaw` must be finite, `duration_s` at most `MAX_TIMEOUT_S` (600 s). The service checks no speed limits: the skills own the motion policy.
- **`move` with a `target`.** A stop condition read from the state store each tick; `duration_s` becomes the cap. `target` is an object so later conditions (a distance, an obstacle guard) sit beside `yaw_rad`; only `yaw_rad` exists. `yaw_rad` is the signed yaw change (CCW +), `lead_s` (≥ 0) the start-ramp time of the open-loop fallback; `vyaw` must be non-zero. The service reads `imu_rpy[2]` before the first `Move` and after each period's wait, sums the per-read deltas wrapped to (−π, π] (so crossing ±π counts the short way), and stops after the period in which the absolute sum reaches `|yaw_rad| − YAW_STOP_MARGIN_RAD` (3°, *tunable*, `skills/robot_service.py`). A read is valid only if the store has a message with `imu_rpy` at most `MAX_STATE_AGE_S` (0.3 s, *tunable*) old; this guard checks the age of what it reads, and there is no general staleness watchdog. Without a valid read the move falls back to open loop at `|vyaw|` and still succeeds: at the start, it runs `|yaw_rad| / |vyaw| + lead_s`; mid-move, it runs the remaining `(|yaw_rad| − |sum|) / |vyaw|` from that tick, without the lead, since the robot is already turning; both rounded to whole periods and capped by `duration_s`. Each fallback is logged on stderr. `measured.yaw_rad` is the sum at the stop (rounded to 0.1 mrad), `null` after a fallback; `measured` is `null` without a `target`. Reaching the cap first is not an error: the reply carries the shorter sum.
- **`action`.** One sport client call from `ACTIONS` (`StandDown`, `Stretch`); `ret` is its code.
- **`fault`.** A [service fault](#fault-injection) to apply during the primitive; accepted only on the sim backend and only with `service_hang`, `service_crash` or `stop_error`, else `bad_request`.
- **While a primitive runs** its connection must send nothing. The handler watches it every `EOF_POLL_S` (0.02 s): EOF ends the lease and stops the robot; any request is `bad_request`, which closes the connection and so also stops it.
- **Errors.** `{"op": "error", "error": {"code", "message"}}`. After `protocol_version` (a message whose `v` is not the service's), `bad_request` (anything malformed: not a JSON object, unknown `op`, a missing or invalid field, `arm` or `disarm` on a connection that is not the control connection, a request while a primitive runs) and `busy` (a second control `hello`) the service closes the connection. After `no_lease` (see [Lease](#lease)), `aborted` (the lease ended while the primitive ran: `the lease ended: <reason>`; whoever ended it sent `StopMove`) and `sdk_exception` (the sport client raised; the service then sent `StopMove`) the connection stays open.

### Lease

Motion needs a lease, so the robot moves only during an armed step and stays stationary during LLM calls ([safety.md](../../docs/safety.md#the-robot-is-stationary-during-llm-calls)) by the service's own rule, not only the dispatcher's.

- **Control connection.** The dispatcher holds one control connection (`hello` with `"role": "control"`); a second one is refused with `busy`. Only it may `arm` and `disarm`.
- **Arm.** `arm(token, timeout_s)` sets the one lease: motion is accepted with `token` until `timeout_s` from now (at most `MAX_TIMEOUT_S`). Arming again ends the current lease first, with `StopMove` if it was used.
- **Binding.** The first connection that sends a primitive with the right token holds the lease; from then on only that connection may move. A primitive is refused with `no_lease` when no lease is armed, the token is missing or wrong, another connection holds the lease, or the deadline has passed. A lease survives its primitives: a skill may send several until the lease ends.
- **End.** The lease ends on `disarm`, `stop`, another `arm`, its deadline (checked every `LEASE_POLL_S`, 0.02 s), EOF on the connection that holds it, EOF on the control connection, the orphan watchdog, or `SIGTERM`. Ending it aborts the running primitive. It sends `StopMove` if the lease was used for motion; `stop`, EOF on the control connection and the orphan watchdog send it always. Every `StopMove` the service sends, for whatever reason, updates the lease's stop record that the [`disarm`](#robot-service) reply reports; `arm` clears it.

Every loss path ends in an explicit `StopMove`, because the robot is assumed to keep its last velocity until one arrives ([robot.md](robot.md#working-assumptions)):

| Loss | Who stops the robot |
|---|---|
| The skill is killed or crashes | The service, on EOF of the lease connection; the dispatcher's `stop` backs it up |
| The step overruns its lease | The service, at the deadline |
| The dispatcher dies | The service, on EOF of the control connection, and its orphan watchdog (`GO2_PARENT_PID`) |
| The service hangs or dies | The dispatcher: no `stop_sent` or `pong` within its wait, or EOF on the control connection, then the fallback `stop_move` process |

**Client** (`robot_ipc.RobotClient`, one thread per client): `RobotClient.connect(path, *, control=False)` connects and exchanges `hello` (its reply is `client.hello`); `state(min_seq=None, wait_s=0.0)` returns a `StateReply(state, rx_mono, link)` with `.seq`; `read_next(wait_s=STATE_WAIT_S)` reads the latest `seq` and then asks for `min_seq` = `seq` + 1, so the answer is the first message that arrived after the call, else the latest earlier one, within `state_store.STATE_WAIT_S` (1.0 s); `subscribe(period_s)` returns the link and `next_event(wait_s)` returns the next `StateReply` sample, a `LinkEvent(link, rx_mono)` or `None` on timeout. Control: `arm(token, timeout_s)`, `disarm()` returning `StopFailure(reason, ret, stop_call_ms)` or `None`, `stop(wait_s)` returning `StopSent(ret, stop_call_ms)`, `ping(wait_s)`. Motion: `move(vx, vy, vyaw, duration_s, *, token, target=None)` (`target` a `MoveTarget(yaw_rad, lead_s)`) returning `MoveResult(duration_s, move_ret, stop_ret, yaw_rad)` (`yaw_rad` the measured change, `None` without a target or after a fallback), waiting `duration_s + SPORT_CLIENT_TIMEOUT_S + REPLY_WAIT_S`, and `action(name, *, token)` returning the code, waiting `SPORT_CLIENT_TIMEOUT_S + REPLY_WAIT_S`. A refusal that keeps the connection (`busy`, `no_lease`, `aborted`, `sdk_exception`) raises `Refused(code, message)`. Every other failure raises `ServiceUnavailable`: nothing listening (`no robot service at <path>: <error>`), `GO2_ROBOT_SOCKET` unset, no reply within the request's wait plus `REPLY_WAIT_S` (2.0 s, *tunable*), the connection lost, or a malformed or closing error reply; another protocol version raises its subclass `ProtocolMismatch`. `robot_ipc.socket_path()` reads `GO2_ROBOT_SOCKET`, `robot_ipc.lease_token()` reads `GO2_LEASE_TOKEN`.

**Skills.** A skill process has one connection, `robot_ipc.session` (`SkillSession`), opened at first use and opened again after a failure; its connect time is `robot_connect_ms`. `runner.StateSampler` samples with `session.read_state()`, which is `read_next()`. A failed sample is `state_error` as always: `ServiceUnavailable: ...`, or `StateUnavailable` when the service has had no message within `STATE_WAIT_S`. `motion.move` and `motion.single_action` send the primitive with `lease_token()` on the same connection; the lease therefore binds to that connection and the skill's death closes it. A `Refused` or `ServiceUnavailable` drops the connection and becomes `motion_rejected`, `robot_unavailable` or `exception` ([error codes](#error-codes)).

**Lifecycle contract** (owned by the dispatcher; the constants are in `skills/robot_service.py`):

- **Start:** `python -m skills.robot_service`, no arguments, working directory the base dir, environment `child_env(...)` with `fault` and `lease_token` unset, so `GO2_ROBOT_SOCKET` is `robot_socket_path(log_dir)` on both sides. Own session, stdin `/dev/null`, stdout a pipe, stderr to a file or inherited, never an unread pipe.
- **Socket and lock:** one service per log dir. At start the service takes an exclusive non-blocking `flock` on `env.robot_lock_path(socket)` = `<log_dir>/robot.lock` and holds it for its lifetime (it writes its PID into the file); the kernel releases it on any exit, `SIGKILL` included. If another process holds it, the service exits with code 3 (`EXIT_LOCKED`) and touches nothing. Holding the lock, it removes a socket file left by a killed service, then listens; the socket file has mode `0600`. Because the path is fixed, any process can attach to a running service by connecting to the socket, without starting one; the dispatcher is its control client. `go2 state` does not attach: it runs the `read_state` utility, with its own DDS, for diagnosis. A Unix socket path is limited to about 107 bytes, so `log.dir` must be short enough for `<log_dir>/robot.sock`.
- **Ready:** exactly one line, `ready` (`READY_LINE`), on stdout once the state source and the sport client are up and the socket listens; nothing else is ever written to stdout. On the real backend the source is up after DDS init and the subscription, before any message has to arrive: the link shows in every reply. Wait up to `STARTUP_TIMEOUT_S` (10.0 s, *tunable*). Exit before the line is a failed start: code 2 means `GO2_BACKEND`, `GO2_ROBOT_SOCKET` or, on the real backend, `GO2_IFACE` is missing or unknown; code 3 the lock; any other code an exception (traceback on stderr), such as DDS init or the sport client failing.
- **Version:** send `hello` first on every connection (`RobotClient.connect` does); `ProtocolMismatch` means the service and the client come from different code and the service must be restarted.
- **Control:** after `ready`, open the control connection and keep it for the service's lifetime. Before each step that may move, `arm` a fresh random token with a deadline that covers the step's timeout, and pass the token to the skill as `GO2_LEASE_TOKEN` (`child_env(..., lease_token=token)`); `disarm` when the step ends; a non-null `stop_failed` in its reply means the service's own `StopMove` failed and the robot may still be moving. Closing the control connection stops the robot.
- **Stop path:** to stop a step, send `stop` on the control connection and kill the skill's process group in parallel ([safety.md](../../docs/safety.md#the-stop-path)). No `stop_sent` within the dispatcher's wait (500 ms, *tunable*), a missing `pong`, or EOF on the control connection means the service is hung or dead: `SIGKILL` it, run the fallback `stop_move` utility. The task ends `ROBOT_SERVICE_LOST` with no further LLM call, and the next task's state read starts the service again.
- **Stop:** `SIGTERM`; it ends the lease (`StopMove` if used), closes the listener, removes the socket file and exits 0. `SIGKILL` after `STOP_GRACE_S` (2.0 s). The lock file stays; it is never removed.
- **Parent death:** the service runs the orphan watchdog (`GO2_PARENT_PID`): it ends the lease and sends `StopMove`, then exits with code 137 about 2 s later, leaving the socket file for the next start to remove. The control connection's EOF usually stops the robot first. Without `GO2_PARENT_PID` (a manual run) it runs until stopped.

## Adding a new skill

Example: a `stand` skill (recommended before experiments, see [roadmap.md](../../docs/roadmap.md#open-questions)).

1. Create `skills/stand.py` by copying `skills/sit.py` (one `action` primitive with a settle wait via `motion.single_action`). A real `stand` would call `StandUp()` then `BalanceStand()`. Each SDK method must be in `robot_ipc.ACTIONS`, in the service's `SportClient` protocol, and on `stub.SimRobot`; a new primitive that is not a single call goes into the robot service.
2. Create `skills/catalog/stand/SKILL.md` with frontmatter (`name: stand`, `entrypoint: skills.stand`, a one-line `description`, `params` if any) and the [body sections](#skillmd-body), written for the planner. If the body quotes a code constant, add it to the prose/constant sync test.
3. If the skill moves the robot, pass `cost=` (a `MotionCost`, or a function of params returning one); a timeout that depends on params is a function too (see `skills/walk.py`). If some observations should reach the model, list them in `context_observations`.
4. Write `body(params)` and end the module with `runner.run_skill(POLICY, body)`, which parses params, samples state before and after, and emits the response. The body returns a frozen `runner.SkillOutcome`, built only with `SkillOutcome.ok(observations=..., timing=...)` or `SkillOutcome.error(code, message, observations=..., timing=...)` so a status without its matching error fields cannot be built; `timing` holds `exec_ms`. Move the robot only through `motion.move` and `motion.single_action`, which ask the robot service; never import `skills.real` or the SDK (the import-linter contract fails). Add a new skill module to that contract's `source_modules` in `pyproject.toml`. Read params directly (`params["key"]`); do not re-check types, enums or ranges, which the dispatcher validates against the `SKILL.md`. Use `backend.sleep()`, never `time.sleep`.
5. Run `uv run go2 catalog`, run the skill by hand (below), and add tests (contract test in `tests/integration/test_skills.py`, policy test in `tests/integration/test_skill_policies.py`). The catalog golden file and the registry hash change: rewrite the golden file with `uv run pytest --update-golden` and review the diff ([testing.md](../../tests/docs/testing.md)).
6. Update this page (and [robot.md](robot.md) if the skill adds robot-side facts).

## Running a skill by hand

On the stub:

```bash
export GO2_BACKEND=stub GO2_STUB_STATE_FILE=logs/.stub_state.json GO2_STUB_TIME_SCALE=0.1
export GO2_ROBOT_SOCKET=logs/robot.sock
uv run python -m skills.robot_service &         # prints "ready"; skills read state and move through it
uv run python -m skills.lease 30 uv run python -m skills.walk '{"direction":"forward","distance_m":1}'
uv run python -m skills.lease 30 uv run python -m skills.turn '{"direction":"left","angle_deg":90}'
export GO2_VISION_SOCKET=logs/.vision.sock GO2_STUB_OBJECTS='{"chair":{"x":1.5,"y":0}}'
uv run python -m skills.vision_service &       # prints "ready"; stop both with: kill %1 %2
uv run python -m skills.detect_object '{"target":"chair"}'
uv run python -m skills.detect_object '{"target":"bottle"}'
GO2_STUB_FAULT=crash uv run python -m skills.sit '{}'; echo "exit=$?"
uv run python -m skills.walk '{"direction":"forward","distance_m":1}'   # no lease: motion_rejected
uv run python -m skills.read_state '{}'
uv run python -m skills.stop_move '{}'
```

The vision service reads `GO2_STUB_OBJECTS` once at its start; restart it after changing the objects. So does the robot service's sim source: restart both after changing the objects. `python -m skills.lease <timeout_s> <command...>` (`skills/lease.py`) does what the dispatcher does for a step: it opens the control connection, arms a random token for `timeout_s`, runs the command with `GO2_LEASE_TOKEN` set, and closes the connection, which ends the lease and sends `StopMove`. It is refused with `busy` while a dispatcher holds the control connection. Without the robot service a skill still runs, with `state_error` instead of states and `robot_unavailable` for any motion. Without `GO2_STUB_STATE_FILE` and `GO2_STUB_TIME_SCALE` the stub uses `logs/.stub_state.json` (relative to the working directory) and 0.1. On the real robot set `GO2_BACKEND=real GO2_IFACE=<nic>` (and `GO2_YOLO_WEIGHTS` for detection), with the robot supervised ([safety.md](../../docs/safety.md#supervised-operation-rules)). Pass all params: skills do not fill defaults.

## Design decisions

- **One subprocess per skill call, never reused; skill processes never touch DDS.** A process per call lets a hung skill be killed by process group, isolates its crashes, and keeps the executor, timeouts, faults and the run log the same for every skill. A fresh process pays no DDS or SDK setup, because the [robot service](#robot-service) owns DDS: a skill process only connects to a socket. Rejected: running skills inside the dispatcher or the service (a hung or crashing skill would take its host down, and the kill-based stop path and per-step isolation would need rebuilding).
- **Skills read state through one long-running robot service; it is the only long-lived DDS subscriber of the sport state.** In a fresh process the subscription, DDS discovery and the first message took about 170–190 ms of every step on the robot, and a fresh process could not create a DDS domain at all while the Ethernet link was unstable; a participant that is already up avoids both, and a read is a socket round trip to a message already in memory. It also gives the dispatcher a fresh state at any time and a continuous stream for logging. The DDS callback only stores the latest message, so readers never wait on the robot and the callback never waits on a reader. Rejected: a shared-memory state buffer (a sub-millisecond gain for real complexity); ZeroMQ or HTTP (a dependency each, no gain over `multiprocessing.connection`); a separate state process beside the motion owner (two lifecycles and two participants without a measured need).
- **The service runs motion primitives; skills keep the policy and send one primitive per motion.** The 10 Hz `Move` loop runs next to the sport client, so its timing does not depend on socket round trips or a skill process being scheduled, and a later obstacle guard or closed-loop motion can act inside the loop where the state is. Skills keep speeds, lead times, direction maps and durations, so the `SKILL.md` sync test and the motion budget still read them in one place. Rejected: skills streaming `Move` through the service as a proxy (one round trip per command, and a stalled skill would stall the command stream without the service knowing why).
- **One sport client in the service sends both motion and every stop.** SDK replies are matched per request id (`unitree_sdk2py/rpc/client_stub.py`) and `Move` never waits for a reply, so a `stop` from a handler thread is never queued behind a running primitive or an action waiting for its reply. Rejected: a separate stop client (a second client with nothing to separate).
- **An action is committed under the lease lock but called outside it, with a trailing `StopMove` if the lease ends during the call.** No action starts after a stop has taken the lock, and a stop never waits on an action's reply (up to `SPORT_CLIENT_TIMEOUT_S`, 5 s). A stop that lands between the commit and the request reaching the robot can still arrive first; the trailing `StopMove` then follows the action. Rejected: holding the lock across the call (a stop would queue behind the reply, which the one-client decision above rules out).
- **Motion needs a lease armed by the dispatcher, bound to one connection, with a deadline the service enforces.** "Stationary during LLM calls" and "only the current step moves" are then enforced where the sport client is, not only in the dispatcher: a stray or late skill, a second client, or a dispatcher bug cannot move the robot. Binding the lease to the skill's connection turns the skill's death into EOF, which the service answers with `StopMove` even if the dispatcher's `stop` is lost. Rejected: trusting the dispatcher's sequencing alone (one bug from motion during planning); a lease without a deadline (a dispatcher that hangs while a step runs would leave it open).
- **Every loss path ends in an explicit `StopMove`: lease connection EOF, deadline, control connection EOF, orphan watchdog, `SIGTERM`, a failed `Move`, an SDK exception.** The robot is assumed to keep its last velocity until `StopMove` ([robot.md](robot.md#working-assumptions)); no path relies on the robot stopping by itself when commands stop arriving.
- **The service reports its own failed `StopMove` once per step, in the `disarm` reply, as the lease's latest `StopMove` if it failed.** The dispatcher sends `disarm` after every step that was not stopped by its own `stop`, and the `stop_sent` reply already carries that stop's code, so the two replies cover every `StopMove` of a step. Every service-sent `StopMove` ends in this one record: the one ending a `move`, a lease deadline, the lease connection's EOF (the skill may be dead and cannot report it) and the `disarm` itself. `disarm` waits for a `StopMove` already decided on another thread, so a skill that died just before cannot race the reply. The latest one counts because a later `StopMove` that returns 0 stops the robot: after a `move` whose `StopMove` failed, the lease's end sends another. Rejected: a skill error code or response field for the `move` stop (a skill response change and a schema bump, and it misses the deadline and the EOF paths, where no skill reports); the first failure since `arm` (it would end a task whose robot a later `StopMove` stopped); a separate status request (one more round trip after every step, and a race with a stop still running).
- **The fresh-process `stop_move` utility stays as the permanent fallback stop.** A hung or dead service cannot send a stop, and its sport client is gone or stuck with it; `stop_move` creates its own DDS participant and sport client and works when nothing else does. `read_state` stays as the diagnosis read that bypasses the service. Both read their robot access from `skills/local.py`, which no skill may import.
- **No staleness watchdog that stops the robot on old state.** If the link is down a `StopMove` does not arrive either, and failed calls already surface the loss. A guard that reads state checks the age of what it reads. Rejected: stopping on old state while moving.
- **A skill's state sample is the first message after the request (`min_seq` = latest `seq` + 1), waiting at most `STATE_WAIT_S`.** This is the freshness rule of an in-process subscription, so samples taken through the service stay comparable with samples taken in the skill process; the latest message alone could predate the skill's own action by up to one message period. Each sample carries `seq` and `age_ms`, so its freshness is visible in the log. The dispatcher may read without `min_seq` where the latest message is fresh enough.
- **The robot service's socket is at a fixed path in `log.dir`, guarded by a lock file.** One robot owner per log dir, and any other client, such as a telemetry reader, can attach to the running service by path. The `flock` is released by the kernel on any exit, so a killed service never blocks the next start, and the socket file is removed only by a process that holds the lock. Rejected: a socket per dispatcher PID, as the vision service uses (nothing else can attach, and two dispatchers could each start a service for the same robot).
- **The service is the only robot path for skills; there is no switch back to per-process DDS.** Two paths would double the code and tests to keep in step; `git revert` is the rollback in development. Rejected: a `robot.io = "process" | "service"` config switch. Kept by design: `stop_move` and `read_state` (above).
- **Every robot service message carries the protocol version, and connections start with `hello`.** The service runs for the whole dispatcher run and other processes attach to it, so a client and a service from different code can meet; the version check turns that into `ProtocolMismatch` instead of misread fields.
- **Detection runs in a long-running [vision service](#vision-service); `detect_object` stays a short process that asks it.** Loading torch and YOLO, the first predict, DDS init and `VideoClient.Init` took about 5 s of every detection on the lab machine, while a warm predict takes 0.04 s. The service pays that once per dispatcher run. The rule above still holds for skills: `detect_object` is one process per call with the same response, timeout and kill path, and the service never touches the sport client, so the clean-channel and kill reasons, which are about motion, do not apply to it. Requests carry only a target and the service grabs a frame per request, so no state leaks between calls. IPC is `multiprocessing.connection` with JSON bytes, standard library only. Rejected: exporting YOLO to ONNX to drop torch from the skill process (still a model load and first inference per call, and a second model format to maintain); streaming frames in the background (camera traffic and a stale-frame question for no gain, since a frame costs one RPC per request); retrying `GetImageSample` on error 3104.
- **`walk` was split into `walk` and `turn`.** The predecessor's single range mixed metres and degrees. Separate skills give the model clearer parameters and allow separate travel and rotation budgets. `turn` uses **degrees** at the interface because that is what operators say; the skill converts to radians.
- **One common JSON response schema for all skills**, replacing the predecessor's three incompatible output formats, so the executor, the log and the context renderer handle every skill the same way.
- **Each skill owns its policy** (timeout formula, motion cost, observations shown to the model) as module constants next to the code that shares them, so a number like walking speed is defined once and tuned in one place.
- **`turn` stops on the measured yaw, inside the service's `move` loop, and stops early by a fixed margin; reaching the cap first still succeeds, with the measured angle reported.** The supervised turns fell short by a start ramp that a fixed lead time only fits at 90° ([robot.md](robot.md#design-decisions)); the robot's own `imu_rpy` yaw measures the turn at any angle. The loop sends `Move` at the constant `YAW_RATE_RPS` and sends `StopMove` once the change is within `YAW_STOP_MARGIN_RAD` (3°) of the target, covering the 1–3° coast measured on the robot; the margin is a property of the robot's coast, not of a skill, so it is a service constant beside the loop that applies it. The target sits on the existing `move` primitive, read in the one loop that already holds the state store, and the cap (`CAP_FACTOR`, `CAP_S`) bounds a robot that turns slowly or not at all. A shortfall is `ok` with `turned_deg` next to `angle_deg`, and `turned_deg` is shown to the model, which can turn again. The motion cost stays the requested angle. Rejected: P-control with slowdown near the target (more tunables, and the Go2's start ramp and minimum effective rate are unmeasured); failing on a shortfall (the model sees `turned_deg` and can replan); a separate op or a second loop for closed-loop motion.
- **Stale or missing yaw during a turn falls back to open loop, and the step succeeds.** The open-loop timing is calibrated on the robot (the lead-time data in [robot.md](robot.md#design-decisions)), so finishing on time usually completes the turn. Without yaw at the start the whole turn runs `|angle| / YAW_RATE_RPS + LEAD_S`; mid-turn the remaining angle runs on time without the lead, since the robot is already turning. The step reports `closed_loop: false` and `turned_deg: null`, not the last measured change, which would understate the turn and invite a needless second turn; `state_after` holds the yaw actually reached. Rejected: stopping and failing (the turn usually completes fine on time); ignoring stale state until the cap (overshoot).
- **`walk` and `turn` share one timeout rule, `motion.motion_timeout`, and one command period, `robot_ipc.CMD_PERIOD_S`,** because both run the same `move` primitive: the fixed overhead and the margin on motion time are properties of that loop, not of a skill, so they are tuned in one place. Speeds (`VELOCITY_MPS`, `YAW_RATE_RPS`) and direction maps stay per skill, since the `SKILL.md` sync test reads them there. Rejected: per-skill copies of `BASE_S` and `FACTOR`, which could drift apart silently.
- **The SDK reply timeout `SPORT_CLIENT_TIMEOUT_S` (5.0 s) must fit inside the timeout of every process whose call reaches the sport client, so a lost reply gives an error response, not a kill.** A kill leaves no response, no `state_after` and no SDK code for the log, while `sdk_error` keeps all three. On the robot, a 90° `turn` whose `StopMove` reply was lost waited the old 10 s and was killed at its 12.4 s timeout. The move-loop base is derived from the SDK timeout, so the two cannot drift; the constant timeouts of `sit`, `stretch` and `stop_move` are checked by a test. Rejected: 2 s (too tight per operator decision); keeping 10 s, which no move-loop or single-action timeout covered.
- **A policy is one frozen `SkillPolicy` dataclass instance per skill, not a subclass per skill.** The skills differ only in data (a name, a constant or a small formula for timeout and cost, an observation list), so a value with optional callables says it in a few lines and the constants sit at module level where `run_skill(POLICY, body)` and the body use them without a class prefix. The dataclass lives in `skills/policy.py`, which imports only the standard library, so the dispatcher's own modules import the type without the runner. Rejected: a `SkillPolicy` base class with one `<Name>Policy` subclass per skill overriding `timeout_s()`/`motion_cost()`; it repeated boilerplate in every module and spread the constants across class attributes, without adding behaviour. The dispatcher still calls `timeout_s(params)` and `motion_cost(params)`, so it does not need to know whether a value is constant.
- **Utilities carry a `POLICY` like skills, as a plain `SkillPolicy` with the default cost and observations.** One mechanism for every module the dispatcher spawns, so the dispatcher reads a utility's name and timeout from its module instead of hard-coding them. The defaults fit both utilities (zero cost: neither commands motion), so a smaller utility-only type would add a second type without a field to drop that matters. Rejected: a `UTILITIES` map in `skills` (a second registry of names and timeouts beside the modules that own them); keeping utility timeouts as dispatcher config keys (`robot.*_timeout_s`), which gave timeouts two sources of truth, config for utilities and `POLICY` for skills.
- **Param and response validation happen on the dispatcher side; the response schema is defined once in `skills`.** Plan params are validated only by the dispatcher's plan and bounds validation against `SKILL.md`; skills read params directly. Skill responses are fully validated only by the dispatcher, but against the dataclasses in `skills/schema.py`, so the skill side constructs the very classes the dispatcher checks and there is no second definition to drift. The one rule that runs in both processes is the error-iff-status check in `SkillResponse.__post_init__`: it is part of the class, costs nothing, and pydantic reports its `ValueError` as a validation error. Rejected: separate skill-side validation of params or response types; the skill-side param checks only mattered for hand-run skills, where a missing key now reports `exception` instead of `invalid_params`.
- **The response schema is standard-library frozen dataclasses (`skills/schema.py`), validated by pydantic only in the dispatcher.** Skill processes must start fast and never import pydantic ([above](#no-side-effects-on-import)), yet the shape must be defined once. pydantic validates dataclasses directly; `__pydantic_config__ = {"extra": "forbid"}` is a plain dict, so `schema.py` needs no pydantic import. `RobotState` forbids extra keys like the other two: `asdict` and pydantic's dump would silently drop them, so a new robot field must be added to the class. A direct constructor call does no type checks, only `__post_init__`; type checks happen when the dispatcher parses the line. Rejected: pydantic models in `skills` (about 80 ms added to every spawn, `stop_move` included); dispatcher-only models plus a test that keeps the skill-side dicts in step (still two definitions); a JSON Schema file (needs code generation or a new dependency); `TypedDict` (pydantic needs `typing_extensions.TypedDict` on Python < 3.12); msgspec (a C dependency in the skill processes).
- **The `SKILL.md` schema and parser belong to `skills` (`skills/manifest.py`)**, so the package that defines the skills owns its catalog contract, and its rules are documented and tested here. pydantic is acceptable there because only the dispatcher process imports the parser; skill subprocesses never do, which an import-linter contract enforces for imports through the repo's own modules ([testing.md](../../tests/docs/testing.md#import-boundaries)). The registry hash stays in the dispatcher, because it also covers the system text and tool schema. Rejected: keeping the schema in the dispatcher's registry, which put the `SKILL.md` contract in the package that only consumes it.
- **The catalog is generated from the registry, never hand-written**, so skill sets of different granularity are presented to the model in the same form and stay comparable.
- **The `SKILL.md` body is model-facing, thin, and in a fixed section template that the parser enforces** (user decision). The planner lacked contract facts it needs to plan (posture preconditions, speeds), and those facts belong next to the skill they describe. The body holds only what the planner needs; human documentation moved to this page and [robot.md](robot.md). The same four headings for every skill and every skill set (granularity tier) keep tiers comparable: what differs between tiers is the skills, not how well or how much each one is described. All sections are required, with `None.` when nothing applies, so every skill has the same shape and a forgotten section is an error rather than a silent gap. The length cap stops bodies growing back into documentation. Mirrored numbers stay literal, guarded by a test, so the model reads plain numbers and the code stays the single source of truth for them. Rejected: frontmatter-only fields (`requires:`, `limits:` keys), because a skill is then just a typed function signature, not really a skill; free-form prose, because its length and quality would vary per skill and tier and confound the granularity comparison; Agent Skills style on-demand loading (the model reads a body only when it asks), because it adds a round-trip per skill and makes the context differ between calls.
- **An unsupported `detect_object` target is a skill error with suggestions; the 80-class COCO list stays out of the catalog.** Listing every class would add tokens to every call; the skill validates the target and suggests close matches, so the model can correct itself on the next call.
- **`detect_object`'s Limits say the camera cannot see an object under, very close to or behind it, so a target lost right after walking toward it was most likely reached or passed.** The model gets no pose or odometry and older sightings drop out of its context, so without this text it read a bottle it had walked past as lost and searched at random until the time limit. The suggested approach step of about 0.3 m is *(tunable)*; the camera offset of about 0.3 m ahead of the body centre that makes an object vanish once passed is *unverified* on the robot ([robot.md](robot.md#object-detection)).
- **State is sampled at the start and end of every step, for logging only.** v1 gives no verdicts. The samples provide data to set v2 verification thresholds before seeing any verification results, and supply the posture shown to the model ([roadmap.md](../../docs/roadmap.md#v2-plan)).
- **The stub replaces only the robot: `SimRobot` is the robot service's sport client on the sim backend**, so process start, the service, the lease, timeouts, kills and both stop paths are exercised for real offline. The sim command stays set until `StopMove`, as assumed for the robot, so a test sees a robot left moving. Rejected: a stub sport client inside the skill process (it would bypass the service the real backend uses).
- **The stub is pose-aware: it integrates commanded velocity and simulates the camera over objects placed in a world, reusing the real detector's classifier.** Detections then change as the robot moves (a chair behind the robot appears after a turn), the state samples carry a pose in the real `position` and `imu_rpy` fields, and position and closeness come from the same thresholds as on the robot (`skills/vision.py`), so the two backends cannot drift apart. Only what the robot supplies is simulated: velocity integration stands in for the robot's motion and estimator, and a pinhole projection stands in for the camera image and YOLO. The projection ignores lens distortion, occlusion and the object's vertical position, and the pose resets only with the posture, never between tasks. Rejected: keeping the static `{class: "position:closeness"}` table (`stub.detections`), alone or beside the world, because it answered the same whatever the robot did, so a plan that turned or walked before looking was never tested against what it would actually see.
- **`skills` owns the process environment contract, the posture type, the error codes, the fault kinds and the stub defaults; the dispatcher imports them.** These are contracts between the executor and the skill processes, and the skill side is where they are read. Defining them once (`skills/env.py`, `schema.Posture`, `schema.ErrorCode`, `stub.FaultKind`, the `stub.DEFAULT_*` values) removes the copies in the executor and config that could drift silently: a renamed variable, a new fault kind or a changed stub default used to need matching edits in both packages. `ErrorCode` is `class ErrorCode(str, Enum)` with `__str__` returning the value, because Python 3.10 has no `StrEnum`; the members serialise and compare as their plain strings, so the response line and the dispatcher's validation are unchanged. `SkillError.code` stays `str`, so pydantic does not reject a code the dispatcher does not know. `Posture` lives in `schema.py` next to `RobotState`, which uses it, rather than in `backend.py`. Rejected: a dispatcher-owned env builder (it would keep the variable names in the package that only sets them); typing `SkillError.code` as `ErrorCode` (an unknown code would turn a skill error into `malformed`).
- **The response is built from four sources, `SkillOutcome` + `StateSampler` + `total_ms` + `setup`, each written by the code that owns it.** The body owns the outcome, the sampler owns the state fields and their timing, the connection owner owns the setup time (`robot_ipc.session` in a skill, `skills/local.py`'s DDS init in a utility), and `run_main` owns the total time and the exception mapping (`SkillOutcome.from_exception`). `run_main` creates the sampler before calling the body, so samples taken before an exception survive without the body writing into a shared result. Accepted edge case: any exception in `stop_move` after `StopMove()` returns (the settle `backend.sleep` on a malformed `GO2_STUB_TIME_SCALE`, or the after-sample raising `BackendNotConfigured`) drops `sdk_ret`, `client_init_ms` and `stop_call_ms` from the response; only misconfiguration reaches it. Rejected: a mutable `ResponseDraft` (a typed version of the old `out` dict: three writers still mutate one object, and it duplicates `SkillResponse`); plain locals in `run_main` with `try/finally` (it either duplicates the exception mapping in each utility or keeps utilities mutating a result argument).
- **Setup cost is its own field (`robot_connect_ms` in a skill, `dds_init_ms` and `client_init_ms` in `stop_move`); `state_ms` measures sampling only and `stop_call_ms` the `StopMove()` call only.** Per-process DDS and sport client setup costs about 1 s on the robot; `stop_move` pays it, a skill pays a socket connect instead. One setup field, or a `state_ms` that includes DDS init, cannot tell DDS from sport client cost, nor sampling from setup. Each field measures one part, so per-step setup can be attributed and kill-to-stop latency is the sum of its parts ([safety.md](../../docs/safety.md#measured-latency)). `dds_init_ms` includes the import of the SDK channel module, because that import loads CycloneDDS and no other field would count it. Rejected: keeping `stop_call_ms` as the whole stop from utility start, because it would again mix DDS, client and call time; the whole stop is `stop_move.duration_ms` in the run log.
- **The dispatcher touches stub state only through `stub.reset(posture, path)`, never the state file or `write_posture`.** The state file layout stays a stub internal, so a richer stub state (the v2 stub upgrade) changes `reset` alone, and posture is read the same way on both backends, through `read_state`. Rejected: a stub `read_posture` call in the dispatcher, which needs a backend branch and a second posture path.
- **The shared skill code is three modules with one reason to change each: `policy.py` (`SkillPolicy`, `MotionCost`, read by the dispatcher), `process.py` (the saved stdout fd and the orphan watchdog) and `runner.py` (`SkillOutcome`, `StateSampler`, response building, `emit`, `run_main`, `run_skill`).** The imports run one way, `runner` → `robot_ipc` → `backend`, and `stub` → `backend`, `process`; `backend` never imports `real` and imports `stub` only inside `backend.sleep`, to keep stub state out of import time. `process` is not named `io`, so it never shadows the standard library module. Rejected: one `result.py` holding all of it, which mixed the dispatcher's policy reads with process plumbing and needed a lazy import cycle with `backend` and `stub`.
- **Skills collapse an error message to one line but do not limit its length; the dispatcher owns the limit.** One limit in one place, so a message is never cut twice to two different lengths, and the run log keeps the skill's full message in `response`. Rejected: a skill-side cap as well (it was 300 characters against the dispatcher's 200, so the skill cut was dead for every view except the logged response).
- **Fault injection by dispatched step number** (error, hang, crash, garbage) covers each step outcome the executor can produce, with real processes. The service faults (`service_hang`, `service_crash`, `stop_error`) are forwarded by the skill and applied in the robot service mid-walk, so the dispatcher's detection of a hung or dead service and its fallback stop are tested with a robot left moving, and `stop_error` tests the service's report of its failed `StopMove` in the `disarm` reply.
- **No `integer` param type.** No skill used it; a whole-number parameter is declared `number`. Full decision in [loop-and-context.md](../../dispatcher/docs/loop-and-context.md).
