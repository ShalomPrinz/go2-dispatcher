# Skills

The `skills` package: the skill runtime (`runner.py`, `motion.py`, `faults.py`) and the five skills with their `SKILL.md` catalog. The process runtime every skill runs on (`SkillOutcome`, `StateSampler`, response building, `emit`, `run_main`) is `contract/runtime.py` ([contract.md](../../contract/docs/contract.md#response-schema)). This page says what a skill is, how the catalog the model sees is generated, and how to add a skill. The robot service the skills move and read state through, the lease, the stub backend and fault injection are in [service.md](../../services/robot/docs/service.md); the vision service `detect_object` asks, its detectors and the stub camera are in [vision.md](../../services/vision/docs/vision.md). The contract a skill follows is in [contract.md](../../contract/docs/contract.md): the [`SKILL.md` frontmatter](../../contract/docs/contract.md#skillmd-frontmatter), [expectations and preconditions](../../contract/docs/contract.md#expectations-and-preconditions) and [body](../../contract/docs/contract.md#skillmd-body), [invocation and environment](../../contract/docs/contract.md#invocation), the [response schema](../../contract/docs/contract.md#response-schema), the [error codes](../../contract/docs/contract.md#error-codes) and the [policies](../../contract/docs/contract.md#policies). Robot-side behaviour (SDK calls, real backend, posture rule, settle waits) is in [robot.md](../../services/robot/docs/robot.md).

A skill has two parts:

1. `skills/catalog/<name>/SKILL.md`: YAML frontmatter that the registry reads, plus a short model-facing body in a fixed section template ([contract.md](../../contract/docs/contract.md#skillmd-body)). This file is the skill's **manifest**: frontmatter plus body sections. Nothing in a `SKILL.md` is for humans; human documentation lives in this page, [contract.md](../../contract/docs/contract.md) and the `robot` docs.
2. `skills/<name>.py`: a module with a `main()` that runs as a subprocess, and a module-level `POLICY` object that the dispatcher reads.

v1 skills: `walk`, `turn`, `sit`, `stretch`, `detect_object`. Two utilities, `services.robot.stop_move` and `services.robot.read_state`, run the same way but are not skills: they have no `SKILL.md` and the model never sees them ([service.md](../../services/robot/docs/service.md#the-package)). Two long-running services support the skills: the [robot service](../../services/robot/docs/service.md#robot-service), which every skill reads robot state through and which runs every motion for them, and the [vision service](../../services/vision/docs/vision.md#vision-service), which `detect_object` asks. The registry loads every subfolder of `skills.dir` that has a `SKILL.md`, so a different skill set (for example another granularity tier) is a different folder ([running.md](../../docs/running.md)).

## Catalog and registry hash

The catalog (`Registry.catalog_text()`) is generated from the frontmatter and the body sections, skills sorted by name, one line per parameter, no trailing newline. The body sections are sent to the model in full, rendered after the parameter lines ([loop-and-context.md](../../dispatcher/docs/loop-and-context.md) has the format). The catalog is sent as `system[1]` = `"## Skills\n" + catalog`. The current catalog is the golden file `dispatcher/tests/golden/catalog.txt`.

Type phrases: `one of a, b`; `text`; `number from X to Y`, `number, at least X`, `number, at most Y` or `number`, followed by the unit.

The **registry hash** is the first 16 hex characters of SHA-256 over `system_text + "\n" + catalog_text + "\n" + json.dumps(tool_schema, sort_keys=True)`. It identifies the whole prompt surface, so it changes with the skill set, any rendered `SKILL.md` frontmatter (every key except `expect` and `requires`) and body wording, the system text and the horizon (which appears in the system text and the tool schema). It is logged in `task_start` and `index.jsonl`; runs with different hashes are not directly comparable. `go2 catalog` prints the system text, catalog, tool schema and hash.

## The skills

| Skill | Action | Observations | Shown to the model on `ok` |
|---|---|---|---|
| `walk` | `move` primitive: `Move` for `distance_m / VELOCITY_MPS + LEAD_S` s, then `StopMove` | `direction`, `distance_m`, `duration_s` (commanded), `sdk_ret` | nothing |
| `turn` | `move` primitive with a yaw target: `Move(0, 0, ±YAW_RATE_RPS)` until the measured yaw change reaches the angle, capped at `radians(angle_deg) / YAW_RATE_RPS × CAP_FACTOR + CAP_S` s, then `StopMove` | `direction`, `angle_deg`, `duration_s`, `sdk_ret`, `closed_loop`, `turned_deg` | `closed_loop`, `turned_deg` |
| `sit` | `action` primitive `StandDown`, then a settle wait | `sdk_ret` | nothing |
| `stretch` | `action` primitive `Stretch`, then a settle wait | `sdk_ret` | nothing |
| `detect_object` | asks the [vision service](../../services/vision/docs/vision.md#vision-service) for one camera frame + YOLO; never moves | `target`, `object_found`, `position` (left/center/right), `closeness` (near/medium/far), `confidence` | `object_found`, `position`, `closeness`, `confidence` |

The skills keep the motion policy (speeds, lead times, direction maps, durations) and send it to the [robot service](../../services/robot/docs/service.md#robot-service) as one primitive; the service runs it. Params and ranges are in each `SKILL.md`. Walk is open loop; turn stops on the measured yaw and falls back to open loop when no fresh yaw is readable ([robot.md](../../services/robot/docs/robot.md#motion)); walk's `left` and `right` are sideways steps that keep the heading. `walk`, `turn` and `stretch` need the robot standing: while sitting, `Move` and `Stretch` return non-zero and the skill reports `sdk_error` (stub behaviour, [service.md](../../services/robot/docs/service.md#stub-backend); *unverified* on the robot). `sit` while already sitting is `ok`. `detect_object` reports the most confident box of the target class; the target must be one of the 80 COCO classes in `services/vision/coco.py`. Not finding an object is `status = ok` with `object_found: false`, not an error.

## No side effects on import

Importing a skill module must do nothing: no SDK import, no DDS init, no argument parsing, no output. All work happens in `main()`, under `if __name__ == "__main__": main()`. At top level a skill imports only the standard library, `contract`, `skills`, the client surface of `services.robot` (`services.robot.protocol`, `services.robot.client`, `services.robot.ramp`; [service.md](../../services/robot/docs/service.md#the-package)) and the client surface of `services.vision` (`services.vision.protocol`, `services.vision.client`, `services.vision.coco`; [vision.md](../../services/vision/docs/vision.md#the-package)). A skill never imports `services.backend` or `services.robot.stub`. Third-party imports happen inside functions: `unitree_sdk2py` in `services/robot/backends/real.py`, and `cv2`, `ultralytics` and `numpy` only in `services/vision/detectors/real.py`, which only the [vision service](../../services/vision/docs/vision.md#vision-service) imports, so no skill process loads torch. The test `tests/integration/test_skills.py::test_fresh_interpreter_import_is_side_effect_free` imports every module of `skills`, `services.robot`, `services.vision` and `contract` (except their tests and `contract.manifest`) in a fresh interpreter and checks that none of `unitree_sdk2py`, `cyclonedds`, `cv2`, `ultralytics` and `numpy` is loaded and that nothing is printed. This is what lets the dispatcher read policies without touching the SDK. A skill process never touches DDS and never loads the detector: the import-linter contract "Skills import only the client surfaces of robot and vision, and no heavy or dispatcher-side package" forbids every module of `skills`, directly or indirectly, from importing `dispatcher`, pydantic, PyYAML, the SDK and detector packages, and any `services.robot` or `services.vision` module outside the client surfaces; the contract table is in [testing.md](../../tests/docs/testing.md#import-boundaries). The `SKILL.md` parser, which needs both, is `contract/manifest.py`; it is imported only by the dispatcher and by tests, never by a skill ([contract.md](../../contract/docs/contract.md#design-decisions)).

The import-linter contracts enforce these rules before every commit and in CI for every import chain through the repo's own modules, including imports inside functions ([testing.md](../../tests/docs/testing.md#import-boundaries)). They treat third-party packages as leaves, so a third-party import that pulls in pydantic or PyYAML (`import anthropic`, at top level or inside a function) passes them, and the fresh-interpreter test checks only the modules it lists; code review is what enforces the import rule above for such imports. That gap is accepted because the rule exists to keep skill spawn time low and already forbids the import.

## Skill faults

The stub's skill faults (`contract.faults.SKILL_FAULTS`: `error`, `hang`, `crash`, `garbage`; [contract.md](../../contract/docs/contract.md#the-package)) arrive in `GO2_STUB_FAULT`, which the dispatcher sets only for the faulted step on the stub backend ([service.md](../../services/robot/docs/service.md#fault-injection)). They act in the skill runtime, `skills/faults.py`, never in a skill body, and nothing about them goes on the wire:

- **`hang`, `crash`, `garbage`:** `runner.run_skill` calls the hook `faults.fire()` once, after it parses the params and samples `state_before` and before the body. `hang` sleeps forever (unscaled), `crash` exits with `CRASH_EXIT_CODE` (139), `garbage` writes `not json` to stdout and exits 0; none emits a response, so the sampled `state_before` is not reported. Because the hook precedes the body, a faulted step also fails before any check in the body: `detect_object` with `crash` and an unsupported target crashes instead of answering `unsupported_object`.
- **`error`:** the helper that would ask a service first calls `faults.injected_error()`, which returns True once, and then returns its own error response without asking: `motion.move` and `motion.single_action` the `sdk_error` response with `sdk_ret` `STUB_ERR_INJECTED` (99), `detect_object` the `camera_unavailable` response.
- A value outside `SKILL_FAULTS` raises `ValueError` in the hook, which the runtime reports as an `exception` error. With the variable unset, nothing happens.
- The utilities (`stop_move`, `read_state`) run on `contract.runtime.run_main` directly, so they never fire a fault.

## Adding a new skill

Example: a `stand` skill (recommended before experiments, see [roadmap.md](../../docs/roadmap.md#open-questions)).

1. Create `skills/stand.py` by copying `skills/sit.py` (one `action` primitive with a settle wait via `motion.single_action`). A real `stand` would call `StandUp()` then `BalanceStand()`. Each SDK method must be in `services.robot.protocol.ACTIONS`, in the service's `SportClient` protocol (`services/robot/service.py`), and on `SimRobot` (`services/robot/backends/sim.py`) ([service.md](../../services/robot/docs/service.md#robot-service)); a new primitive that is not a single call goes into the robot service.
2. Create `skills/catalog/stand/SKILL.md` with frontmatter (`name: stand`, `entrypoint: skills.stand`, a one-line `description`, `params` if any) and the [body sections](../../contract/docs/contract.md#skillmd-body), written for the planner. If the body quotes a code constant, add it to the prose/constant sync test.
3. If the skill moves the robot, pass `cost=` (a `MotionCost`, or a function of params returning one); a timeout that depends on params is a function too (see `skills/walk.py`). If some observations should reach the model, list them in `context_observations`.
4. Write `body(params)` and end the module with `runner.run_skill(POLICY, body)`, which parses params, samples state before and after, and emits the response. The body returns a frozen `SkillOutcome` (`contract/runtime.py`), built only with `SkillOutcome.ok(observations=..., timing=...)` or `SkillOutcome.error(code, message, observations=..., timing=...)` so a status without its matching error fields cannot be built; `timing` holds `exec_ms`. Move the robot only through `motion.move` and `motion.single_action`, which ask the robot service; never import `services.robot.backends` or the SDK (the import-linter contract fails). The contract covers the whole `skills` package, so a new skill module needs no change in `pyproject.toml`. Read params directly (`params["key"]`); do not re-check types, enums or ranges, which the dispatcher validates against the `SKILL.md`. Use `backend.sleep()` (`contract/backend.py`), never `time.sleep`.
5. Run `uv run go2 catalog`, run the skill by hand (below), and add tests (contract test in `tests/integration/test_skills.py`, policy test in `tests/integration/test_skill_policies.py`). The catalog golden file and the registry hash change: rewrite the golden file with `uv run pytest --update-golden` and review the diff ([testing.md](../../tests/docs/testing.md)).
6. Update this page (and [robot.md](../../services/robot/docs/robot.md) if the skill adds robot-side facts).

## Running a skill by hand

On the stub:

```bash
export GO2_BACKEND=stub GO2_STUB_STATE_FILE=logs/.stub_state.json GO2_STUB_TIME_SCALE=0.1
export GO2_ROBOT_SOCKET=logs/robot.sock
uv run python -m services.robot.service &                # prints "ready"; skills read state and move through it
uv run python -m services.robot.lease 30 uv run python -m skills.walk '{"direction":"forward","distance_m":1}'
uv run python -m services.robot.lease 30 uv run python -m skills.turn '{"direction":"left","angle_deg":90}'
export GO2_VISION_SOCKET=logs/.vision.sock GO2_STUB_OBJECTS='{"chair":{"x":1.5,"y":0}}'
uv run python -m services.vision.service &              # prints "ready"; stop both with: kill %1 %2
uv run python -m skills.detect_object '{"target":"chair"}'
uv run python -m skills.detect_object '{"target":"bottle"}'
GO2_STUB_FAULT=crash uv run python -m skills.sit '{}'; echo "exit=$?"
uv run python -m skills.walk '{"direction":"forward","distance_m":1}'   # no lease: motion_rejected
uv run python -m services.robot.read_state '{}'
uv run python -m services.robot.stop_move '{}'
```

The vision service reads `GO2_STUB_OBJECTS` once at its start; restart it after changing the objects. So does the robot service's sim source: restart both after changing the objects. `python -m services.robot.lease <timeout_s> <command...>` (`services/robot/lease.py`) does what the dispatcher does for a step: it opens the control connection, arms a random token for `timeout_s`, runs the command with `GO2_LEASE_TOKEN` set, and closes the connection, which ends the lease and sends `StopMove`. It is refused with `busy` while a dispatcher holds the control connection. Without the robot service a skill still runs, with `state_error` instead of states and `robot_unavailable` for any motion. Without `GO2_STUB_STATE_FILE` and `GO2_STUB_TIME_SCALE` the stub uses `logs/.stub_state.json` (relative to the working directory) and 0.1. On the real robot set `GO2_BACKEND=real GO2_IFACE=<nic>` (and `GO2_YOLO_WEIGHTS` for detection), with the robot supervised ([safety.md](../../docs/safety.md#supervised-operation-rules)). Pass all params: skills do not fill defaults.

## Design decisions

- **One subprocess per skill call, never reused; skill processes never touch DDS.** A process per call lets a hung skill be killed by process group, isolates its crashes, and keeps the executor, timeouts, faults and the run log the same for every skill. A fresh process pays no DDS or SDK setup, because the [robot service](../../services/robot/docs/service.md#robot-service) owns DDS: a skill process only connects to a socket. Rejected: running skills inside the dispatcher or the service (a hung or crashing skill would take its host down, and the kill-based stop path and per-step isolation would need rebuilding).
- **`walk` was split into `walk` and `turn`.** The predecessor's single range mixed metres and degrees. Separate skills give the model clearer parameters and allow separate travel and rotation budgets. `turn` uses **degrees** at the interface because that is what operators say; the skill converts to radians.
- **`turn` stops on the measured yaw, inside the service's `move` loop, and stops early by a fixed margin; reaching the cap first still succeeds, with the measured angle reported.** The supervised turns fell short by a start ramp that a fixed lead time only fits at 90° ([robot.md](../../services/robot/docs/robot.md#design-decisions)); the robot's own `imu_rpy` yaw measures the turn at any angle. The loop sends `Move` at the constant `YAW_RATE_RPS` and sends `StopMove` once the change is within `YAW_STOP_MARGIN_RAD` (3°) of the target, covering the 1–3° coast measured on the robot; the margin is a property of the robot's coast, not of a skill, so it is a service constant beside the loop that applies it. The target sits on the existing `move` primitive, read in the one loop that already holds the state store, and the cap (`CAP_FACTOR`, `CAP_S`) bounds a robot that turns slowly or not at all. A shortfall is `ok` with `turned_deg` next to `angle_deg`, and `turned_deg` is shown to the model, which can turn again. The motion cost stays the requested angle. Rejected: P-control with slowdown near the target (more tunables, and the Go2's start ramp and minimum effective rate are unmeasured); failing on a shortfall (the model sees `turned_deg` and can replan); a separate op or a second loop for closed-loop motion.
- **Stale or missing yaw during a turn falls back to open loop, and the step succeeds.** The open-loop timing is calibrated on the robot (the lead-time data in [robot.md](../../services/robot/docs/robot.md#design-decisions)), so finishing on time usually completes the turn. Without yaw at the start the whole turn runs `|angle| / YAW_RATE_RPS + LEAD_S`; mid-turn the remaining angle runs on time without the lead, since the robot is already turning. The step reports `closed_loop: false` and `turned_deg: null`, not the last measured change, which would understate the turn and invite a needless second turn; `state_after` holds the yaw actually reached. Rejected: stopping and failing (the turn usually completes fine on time); ignoring stale state until the cap (overshoot).
- **`walk` and `turn` share one timeout rule, `motion.motion_timeout`, and one command period, `services.robot.protocol.CMD_PERIOD_S`,** because both run the same `move` primitive: the fixed overhead and the margin on motion time are properties of that loop, not of a skill, so they are tuned in one place. Speeds (`VELOCITY_MPS`, `YAW_RATE_RPS`) and direction maps stay per skill, since the `SKILL.md` sync test reads them there. Rejected: per-skill copies of `BASE_S` and `FACTOR`, which could drift apart silently.
- **The catalog is generated from the registry, never hand-written**, so skill sets of different granularity are presented to the model in the same form and stay comparable.
- **An unsupported `detect_object` target is a skill error with suggestions; the 80-class COCO list stays out of the catalog.** Listing every class would add tokens to every call; the skill validates the target and suggests close matches, so the model can correct itself on the next call.
- **`detect_object`'s Limits say the camera cannot see an object under, very close to or behind it, so a target lost right after walking toward it was most likely reached or passed.** The model gets no pose or odometry and older sightings drop out of its context, so without this text it read a bottle it had walked past as lost and searched at random until the time limit. The suggested approach step of about 0.3 m is *(tunable)*; the camera offset of about 0.3 m ahead of the body centre that makes an object vanish once passed is *unverified* on the robot ([vision.md](../../services/vision/docs/vision.md#object-detection)).
- **State is sampled at the start and end of every step.** The samples are logged, feed the dispatcher's fault detection and goal verification ([loop-and-context.md](../../dispatcher/docs/loop-and-context.md#verification)), and supply the posture shown to the model.
- **Skill faults fire from one hook in `run_skill` and one `injected_error()` check, never from a skill.** A skill body stays free of stub code, and every skill gets the same fault at the same point. The hook fires before the body rather than at the first service call: a `detect_object` step with a fault and an unsupported target, or with the vision service down, gets the fault instead of that error (accepted). `error` stays a check in the helpers so each keeps its own error response. Rejected: firing at each helper's first service call (every helper must remember to call it), and turning `error` into a hook fault with one generic response (it would change the responses).
- **`runner.py` holds only what is skill-specific: `run_skill` and its state sampler, which reads through the robot service's `session` with the connect as `prepare`.** The process runtime the utilities share (`SkillOutcome`, `StateSampler`, response building, `emit`, `run_main`) is `contract/runtime.py`, beside the policy types (`contract/policy.py`), the process resources (`contract/process.py`) and backend selection (`contract/backend.py`) ([contract.md](../../contract/docs/contract.md#design-decisions)). The imports run one way: `runner` → `services.robot.client` → `services.robot.protocol` → `contract`. Rejected: one `result.py` holding all of it, which mixes the dispatcher's policy reads with process plumbing.
