# Robot service

The `robot` package: the robot service, its protocol and client, the lease, the backends (the real Go2 and the sim), and fault injection. The stub state file and DDS init are shared with the vision service in `services.backend` ([backend.md](../../backend/docs/backend.md)). Robot facts, SDK usage, state sampling and the posture rule are in [robot.md](robot.md); the skills that use the service are in [skills.md](../../../skills/docs/skills.md); the contract is in [contract.md](../../../contract/docs/contract.md); stopping the robot is in [safety.md](../../../docs/safety.md).

**Client surface.** `skills` and `dispatcher` import only `services.robot.protocol`, `services.robot.client`, and `services.robot.ramp`; the dispatcher also imports `services.robot.stub` (`protocol` imports `services.robot.state_store`, `stub` imports `services.backend.stub_state`). None of these loads a backend, the service, the SDK, pydantic or PyYAML. The dispatcher additionally imports the two utility modules, `services.robot.stop_move` and `services.robot.read_state`, for their module name and `POLICY`; that import loads the backend interface (`services.robot.backends`) into the dispatcher process, but no backend module: `load()` imports one only when called. It is a named exception in the import contracts ([testing.md](../../../tests/docs/testing.md#import-boundaries)), pending removal ([roadmap.md](../../../docs/roadmap.md#import-contract-exceptions)). `robot` imports `contract` and `services.backend` only. The utilities `stop_move` and `read_state` run on the process runtime `contract.runtime` (`run_main`, `StateSampler`, `SkillOutcome`, `parse_params`), because a utility emits the skill response ([contract.md](../../../contract/docs/contract.md#response-schema)).

## Robot backends

The robot service and the utilities reach the robot only through one `RobotBackend` object, which `backends.load()` returns: the entry for `GO2_BACKEND` in its table `BACKENDS` (`contract.backend.select`, [contract.md](../../../contract/docs/contract.md#the-package)), built once per process; a missing or unknown name raises `BackendNotConfigured`. Each entry imports its module only when called, so on the real backend `load()` and the utilities import no sim or stub code, and importing the loader needs only the standard library. The robot service imports no backend module either: `Motion` knows only the sport client, the motion clock, the state store and the arm hook that `motion(store)` returns. Adding a backend is one module and one table entry.

| Member | Used by | Real (`backends/real.py`, `RealBackend`) | Sim (`backends/sim.py`, `SimBackend`) |
|---|---|---|---|
| `name` | the service's `hello` | `real` | `stub` |
| `init_dds()` | utilities, before a sample and the sport client | `services.backend.dds.init_dds()` | records an init, no DDS |
| `setup_timing()` | utilities, as `timing.dds_init_ms` | the process's DDS init time, if attempted | 0.0 once `init_dds` ran |
| `sport_client()` | `stop_move`: a fresh client in its process | `real.get_sport_client()` | a new `SimRobot` |
| `sample_state()` | utilities: one sample without the service | its own `rt/sportmodestate` subscription ([robot.md](robot.md#state-sampling)) | `sim.sample_state()` |
| `start_source()` | the service: its store and what keeps it fed | the `rt/sportmodestate` subscriber | a thread sampling the stub every `SIM_PERIOD_S` |
| `motion(store)` | the service: its one sport client, motion clock and arm hook | `SportClient`; real time (`abort.wait`); a hook that does nothing | `FaultySportClient` around a `SimRobot`; `SimRobot.wait`, then a state published to `store`; `FaultFileArm`, which clears the wrapper and takes the [fault file](#fault-injection) into it (a stale file is dropped when `motion` is called, at service start) |
| `sleep(seconds)` | `stop_move`'s settle wait | `time.sleep` | `stub_sleep` (scaled) |

`backends.setup_timing()` is the utilities' setup timing: the backend's, or empty when the backend is not configured. `Motion.arm` calls the arm hook in two steps under its lock: `clear()` before the old lease ends, so its `StopMove` (if the lease was used) runs with the old lease's faults cleared, and `arm()` after it has ended and before the new lease exists, so a new fault can never fire on the old primitive. A `ValueError` from `arm()` leaves no lease and the service answers `bad_request`. The utilities' `sport_client()` is a bare `SimRobot`, so the fallback stop never sees a fault.

## Robot service

Skills never touch DDS. The robot service (`services/robot/service.py`) is a long-running process and the only long-lived DDS owner of the robot's sport state and motion. It holds the state source and **one sport client**, created at start and used for every motion primitive and every stop:

- **State.** On the real backend it subscribes to `rt/sportmodestate` once at start ([robot.md](robot.md#state-sampling)); on the sim backend (`GO2_BACKEND=stub`) its sim source (`SimBackend.start_source()`) puts `sim.sample_state()` into the same store every `SIM_PERIOD_S` (0.02 s, *tunable*). Either way a `state_store.StateStore` holds only the latest message, numbered `seq` from 1 and stamped `rx_mono` (`time.monotonic()`, CLOCK_MONOTONIC, comparable only on the same host) by the callback, which does nothing else; mapping to `RobotState` happens when a client reads.
- **Motion.** The sport client and motion clock come from the backend's `motion(store)`. Real: one `SportClient` (`real.get_sport_client()`, after the state subscription's DDS init); sim: `sim.SimRobot` over the stub state file ([stub backend](#stub-backend)), so the stub runs the same process shape. Primitives run one at a time on the service's motion loop thread; a lease deadline thread and one handler thread per connection run beside it. One lock guards the lease and serialises every `Move` with the abort of its primitive, so no `Move` follows a stop. An action (`StandDown`, `Stretch`) waits for its SDK reply, so only its commit is under the lock: the abort check and taking the call, after which a stop no longer prevents it; the call itself runs outside the lock. If the lease ends during the call, the motion loop sends a trailing `StopMove` after the reply and the step is aborted, so `StopMove` is the last command either way. `StopMove` itself is sent from whichever thread ends the motion, outside the lock ([robot.md](robot.md#motion)).
- **Clocks.** `StateStore(to_state, clock=time.monotonic)` stamps arrivals with its `clock` and measures `age_ms` and the link with it; `Motion(..., clock=time.monotonic)` sets and checks the lease deadline with its own. The service always uses the defaults; tests pass a clock they advance, so freshness, link and deadline do not depend on machine load. Waits for a message, the deadline poll and the `StopMove` timing always use real time.

**Protocol** (`services/robot/protocol.py`, `PROTOCOL_VERSION` 1). `multiprocessing.connection` over the Unix socket at `GO2_ROBOT_SOCKET`, encoded as for the [vision service](../../vision/docs/vision.md#vision-service) (`contract/wire.py`, [contract.md](../../../contract/docs/contract.md#wire-framing): UTF-8 JSON objects with `send_bytes`, never pickle), at most `MAX_MESSAGE_BYTES`. Connections are persistent: a client sends any number of requests on one connection, one at a time, and the service serves each connection on its own thread. Every message, both ways, is `{"v": 1, "op": ..., ...}`.

| Request | Connection | Reply |
|---|---|---|
| `{"op": "hello"}`, or `{"op": "hello", "role": "control"}` | any | `{"op": "hello", "backend": "real" \| "stub", "pid": int}` |
| `{"op": "state", "min_seq": int \| null, "wait_ms": number}` | any | `{"op": "state", "state": RobotState \| null, "rx_mono": number \| null, "link": "up" \| "down"}` |
| `{"op": "subscribe", "period_ms": number}` | any | `{"op": "subscribed", "period_ms": number, "link": ...}`, then the stream below |
| `{"op": "ping"}` | any | `{"op": "pong"}` |
| `{"op": "stop"}` | any | `{"op": "stop_sent", "ret": int \| null, "stop_call_ms": number}` |
| `{"op": "arm", "token": str, "timeout_s": number}` | control | `{"op": "armed", "token": str, "timeout_s": number}` |
| `{"op": "disarm"}` | control | `{"op": "disarmed", "stop_failed": {"reason": str, "ret": int \| null, "stop_call_ms": number} \| null}` |
| `{"op": "move", "token": str, "vx", "vy", "vyaw": number, "duration_s": number, "target"?: {"yaw_rad": number, "lead_s": number}}` | lease | `{"op": "move", "duration_s": number, "move_ret": int, "stop_ret": int \| null, "measured": {"yaw_rad": number \| null} \| null}` |
| `{"op": "action", "token": str, "name": "StandDown" \| "Stretch"}` | lease | `{"op": "action", "ret": int}` |

- **`state`.** With `min_seq`, the service waits up to `wait_ms` (capped at `MAX_STATE_WAIT_S`, 5 s) for a message with `seq` ≥ `min_seq`; if none comes it answers with the latest earlier message. Without `min_seq` it answers at once. `state` is the `RobotState` mapped at the read, with `t` the read time, `seq` and `age_ms` (read time minus `rx_mono`); it is `null` while the service has had no message. `link` is `up` if the latest message is at most `state_store.LINK_GAP_S` (0.5 s, *tunable*) old, else `down`.
- **Stream.** After `subscribe` the connection only receives. Every `period_ms` (at least `MIN_STREAM_PERIOD_S`, 0.02 s) the service sends `{"op": "link", "link": ..., "rx_mono": ...}` if the link changed since the last check (`rx_mono` of the latest message then: for `down` the last one before the gap), then `{"op": "sample", ...}`, shaped like a `state` reply, if a message newer than the last one sent has arrived. A gap therefore shows as a `down` event, no samples, and an `up` event; its length is the next sample's `rx_mono` minus the `down` event's `rx_mono`, to within one period. The stream ends when the client closes the connection.
- **`stop`.** Ends any lease, aborts the running primitive and sends `StopMove` from the handler thread, whatever the state; the reply comes after `StopMove` returns. `ret` is its code (`null` if it raised) and `stop_call_ms` the call's time in the service. Accepted on any connection, so a stop never waits for a role.
- **`disarm`.** Ends the lease (`StopMove` if it was used), then waits until every `StopMove` the service has already decided to send has returned, whichever thread sends it, so a stop on the lease connection's EOF that is still running is included. `stop_failed` is the latest of those `StopMove`s since the `arm` if it failed (non-zero `ret`, or `ret` `null` if it raised), else `null`: `reason` is why the service sent it (for example `move done`, `lease deadline`, `lease connection closed`, `disarmed`) and `stop_call_ms` the call's time. A later `StopMove` that returns 0 clears it. A non-null `stop_failed` means the robot may still be moving.
- **`move`.** `Move(vx, vy, vyaw)` every `CMD_PERIOD_S` (0.1 s), `max(1, round(duration_s / CMD_PERIOD_S))` times, then `StopMove`. `duration_s` in the reply is the `Move`s sent × period; `move_ret` is the failing `Move`'s code (0 if none failed; the loop then stops at once and sends `StopMove`); `stop_ret` is the closing `StopMove`'s code. `vx`, `vy`, `vyaw` must be finite, `duration_s` at most `MAX_TIMEOUT_S` (600 s). The service checks no speed limits: the skills own the motion policy.
- **`move` with a `target`.** A stop condition read from the state store each tick; `duration_s` becomes the cap. `target` is an object so later conditions (a distance, an obstacle guard) sit beside `yaw_rad`; only `yaw_rad` exists. `yaw_rad` is the signed yaw change (CCW +), `lead_s` (≥ 0) the start-ramp time of the open-loop fallback; `vyaw` must be non-zero. The service reads `imu_rpy[2]` before the first `Move` and after each period's wait, sums the per-read deltas wrapped to (−π, π] (so crossing ±π counts the short way), and stops after the period in which the absolute sum reaches `|yaw_rad| − YAW_STOP_MARGIN_RAD` (3°, *tunable*, `services/robot/service.py`). A read is valid only if the store has a message with `imu_rpy` at most `MAX_STATE_AGE_S` (0.3 s, *tunable*) old; this guard checks the age of what it reads, and there is no general staleness watchdog. Without a valid read the move falls back to open loop at `|vyaw|` and still succeeds: at the start, it runs `|yaw_rad| / |vyaw| + lead_s`; mid-move, it runs the remaining `(|yaw_rad| − |sum|) / |vyaw|` from that tick, without the lead, since the robot is already turning; both rounded to whole periods and capped by `duration_s`. Each fallback is logged on stderr. `measured.yaw_rad` is the sum at the stop (rounded to 0.1 mrad), `null` after a fallback; `measured` is `null` without a `target`. Reaching the cap first is not an error: the reply carries the shorter sum.
- **`action`.** One sport client call from `ACTIONS` (`StandDown`, `Stretch`); `ret` is its code.
- **`arm` on the stub.** The sim backend's arm hook takes the [fault file](#fault-injection); a bad fault file is `bad_request`. The messages are the same on both backends: no message carries a fault.
- **While a primitive runs** its connection must send nothing. The handler watches it every `EOF_POLL_S` (0.02 s): EOF ends the lease and stops the robot; any request is `bad_request`, which closes the connection and so also stops it.
- **Errors.** `{"op": "error", "error": {"code", "message"}}`. After `protocol_version` (a message whose `v` is not the service's), `bad_request` (anything malformed: not a JSON object, unknown `op`, a missing or invalid field, `arm` or `disarm` on a connection that is not the control connection, a request while a primitive runs) and `busy` (a second control `hello`) the service closes the connection. After `no_lease` (see [Lease](#lease)), `aborted` (the lease ended while the primitive ran: `the lease ended: <reason>`; whoever ended it sent `StopMove`) and `sdk_exception` (the sport client raised; the service then sent `StopMove`) the connection stays open.

### Lease

Motion needs a lease, so the robot moves only during an armed step and stays stationary during LLM calls ([safety.md](../../../docs/safety.md#the-robot-is-stationary-during-llm-calls)) by the service's own rule, not only the dispatcher's.

- **Control connection.** The dispatcher holds one control connection (`hello` with `"role": "control"`); a second one is refused with `busy`. Only it may `arm` and `disarm`.
- **Arm.** `arm(token, timeout_s)` sets the one lease: motion is accepted with `token` until `timeout_s` from now (at most `MAX_TIMEOUT_S`). Arming again ends the current lease first, with `StopMove` if it was used.
- **Binding.** The first connection that sends a primitive with the right token holds the lease; from then on only that connection may move. A primitive is refused with `no_lease` when no lease is armed, the token is missing or wrong, another connection holds the lease, or the deadline has passed. A lease survives its primitives: a skill may send several until the lease ends.
- **End.** The lease ends on `disarm`, `stop`, another `arm`, its deadline (checked every `LEASE_POLL_S`, 0.02 s), EOF on the connection that holds it, EOF on the control connection, the orphan watchdog, or `SIGTERM`. Ending it aborts the running primitive. It sends `StopMove` if the lease was used for motion; `stop`, EOF on the control connection and the orphan watchdog send it always. Every `StopMove` the service sends, for whatever reason, updates the lease's stop record that the [`disarm`](#robot-service) reply reports; `arm` clears it.

Every loss path ends in an explicit `StopMove`, because the robot is assumed to keep its last velocity until one arrives ([robot.md](robot.md#working-assumptions)):

| Loss | Who stops the robot |
|---|---|
| The skill is killed or crashes | The service, on EOF of the lease connection; the dispatcher's `stop` backs it up |
| The step overruns its lease | The service, at the deadline |
| The dispatcher dies | The service, on EOF of the control connection, and its orphan watchdog (`GO2_PARENT_PID`) |
| The service hangs or dies | The dispatcher: no `stop_sent` or `pong` within its wait, or EOF on the control connection, then the fallback `stop_move` process |

**Client** (`client.RobotClient` in `services/robot/client.py`, one thread per client): `RobotClient.connect(path, *, control=False)` connects and exchanges `hello` (its reply is `client.hello`); `state(min_seq=None, wait_s=0.0)` returns a `StateReply(state, rx_mono, link)` with `.seq`; `read_next(wait_s=STATE_WAIT_S)` reads the latest `seq` and then asks for `min_seq` = `seq` + 1, so the answer is the first message that arrived after the call, else the latest earlier one, within `state_store.STATE_WAIT_S` (1.0 s); `subscribe(period_s)` returns the link and `next_event(wait_s)` returns the next `StateReply` sample, a `LinkEvent(link, rx_mono)` or `None` on timeout. Control: `arm(token, timeout_s)`, `disarm()` returning `StopFailure(reason, ret, stop_call_ms)` or `None`, `stop(wait_s)` returning `StopSent(ret, stop_call_ms)`, `ping(wait_s)`. Motion: `move(vx, vy, vyaw, duration_s, *, token, target=None)` (`target` a `MoveTarget(yaw_rad, lead_s)`) returning `MoveResult(duration_s, move_ret, stop_ret, yaw_rad)` (`yaw_rad` the measured change, `None` without a target or after a fallback), waiting `duration_s + SPORT_CLIENT_TIMEOUT_S + REPLY_WAIT_S`, and `action(name, *, token)` returning the code, waiting `SPORT_CLIENT_TIMEOUT_S + REPLY_WAIT_S`. A refusal that keeps the connection (`busy`, `no_lease`, `aborted`, `sdk_exception`) raises `Refused(code, message)`. Every other failure raises `ServiceUnavailable`: nothing listening (`no robot service at <path>: <error>`), `GO2_ROBOT_SOCKET` unset, no reply within the request's wait plus `REPLY_WAIT_S` (2.0 s, *tunable*), the connection lost, or a malformed or closing error reply; another protocol version raises its subclass `ProtocolMismatch`. `client.socket_path()` reads `GO2_ROBOT_SOCKET`, `client.lease_token()` reads `GO2_LEASE_TOKEN`.

**Skills.** A skill process has one connection, `client.session` (`SkillSession`), opened at first use and opened again after a failure; its connect time is `robot_connect_ms`. The skill's `contract.runtime.StateSampler` (built in `skills/runner.py`) samples with `session.read_state()`, which is `read_next()`. A failed sample is `state_error` as always: `ServiceUnavailable: ...`, or `StateUnavailable` when the service has had no message within `STATE_WAIT_S`. `motion.move` and `motion.single_action` send the primitive with `lease_token()` on the same connection; the lease therefore binds to that connection and the skill's death closes it. A `Refused` or `ServiceUnavailable` drops the connection and becomes `motion_rejected`, `robot_unavailable` or `exception` ([error codes](../../../contract/docs/contract.md#error-codes)).

**Lifecycle contract** (owned by the dispatcher; the constants are in `services/robot/protocol.py`):

- **Start:** `python -m services.robot.service` (`protocol.SERVICE_MODULE`), no arguments, working directory the base dir, environment `child_env(...)` with `fault` and `lease_token` unset, so `GO2_ROBOT_SOCKET` is `robot_socket_path(log_dir)` on both sides. Own session, stdin `/dev/null`, stdout a pipe, stderr to a file or inherited, never an unread pipe.
- **Socket and lock:** one service per log dir. At start the service takes an exclusive non-blocking `flock` on `env.robot_lock_path(socket)` = `<log_dir>/robot.lock` and holds it for its lifetime (it writes its PID into the file); the kernel releases it on any exit, `SIGKILL` included. If another process holds it, the service exits with code 3 (`EXIT_LOCKED`) and touches nothing. Holding the lock, it removes a socket file left by a killed service, then listens; the socket file has mode `0600`. Because the path is fixed, any process can attach to a running service by connecting to the socket, without starting one; the dispatcher is its control client. `go2 state` does not attach: it runs the `read_state` utility, with its own DDS, for diagnosis. A Unix socket path is limited to about 107 bytes, so `log.dir` must be short enough for `<log_dir>/robot.sock`.
- **Ready:** exactly one line, `ready` (`READY_LINE`), on stdout once the state source and the sport client are up and the socket listens; nothing else is ever written to stdout. On the real backend the source is up after DDS init and the subscription, before any message has to arrive: the link shows in every reply. Wait up to `STARTUP_TIMEOUT_S` (10.0 s, *tunable*). Exit before the line is a failed start: code 2 means `GO2_BACKEND`, `GO2_ROBOT_SOCKET` or, on the real backend, `GO2_IFACE` is missing or unknown; code 3 the lock; any other code an exception (traceback on stderr), such as DDS init or the sport client failing.
- **Version:** send `hello` first on every connection (`RobotClient.connect` does); `ProtocolMismatch` means the service and the client come from different code and the service must be restarted.
- **Control:** after `ready`, open the control connection and keep it for the service's lifetime. Before each step that may move, `arm` a fresh random token with a deadline that covers the step's timeout, and pass the token to the skill as `GO2_LEASE_TOKEN` (`child_env(..., lease_token=token)`); `disarm` when the step ends; a non-null `stop_failed` in its reply means the service's own `StopMove` failed and the robot may still be moving. Closing the control connection stops the robot.
- **Stop path:** to stop a step, send `stop` on the control connection and kill the skill's process group in parallel ([safety.md](../../../docs/safety.md#the-stop-path)). No `stop_sent` within the dispatcher's wait (500 ms, *tunable*), a missing `pong`, or EOF on the control connection means the service is hung or dead: `SIGKILL` it, run the fallback `stop_move` utility. The task ends `ROBOT_SERVICE_LOST` with no further LLM call, and the next task's state read starts the service again.
- **Stop:** `SIGTERM`; it ends the lease (`StopMove` if used), closes the listener, removes the socket file and exits 0. `SIGKILL` after `STOP_GRACE_S` (2.0 s). The lock file stays; it is never removed.
- **Parent death:** the service runs the orphan watchdog (`GO2_PARENT_PID`): it ends the lease and sends `StopMove`, then exits with code 137 about 2 s later, leaving the socket file for the next start to remove. The control connection's EOF usually stops the robot first. Without `GO2_PARENT_PID` (a manual run) it runs until stopped.

## Stub backend

The stub replaces only the robot: its sport client is `sim.SimRobot` (`services/robot/backends/sim.py`), which the [robot service](#robot-service) runs as its one sport client on the sim backend (and `stop_move` creates in its own process), so processes, the lease, timeouts, kills and both stop paths run for real. It simulates only what the real backend gets from the robot: motion and the state message here, the camera image in the [stub camera](../../vision/docs/vision.md#stub-camera). The sim's constants are in `services/robot/backends/sim.py`; the state file is `services/backend/stub_state.py` ([backend.md](../../backend/docs/backend.md#stub-state-file)), and the stub world's format (postures, conditions, objects, defaults) is `contract/stub.py` ([contract.md](../../../contract/docs/contract.md#the-package)).

It keeps posture, an odometry pose, the running velocity command, the start ramp's progress (`sequence_s`) and a [robot fault](#robot-faults) `condition` in one JSON state file, whose format and writers are in [backend.md](../../backend/docs/backend.md#stub-state-file).

| Call | While standing | While sitting |
|---|---|---|
| `Move` | 0 | 1 (not standing) |
| `StopMove` | 0 | 0 |
| `StandDown` | 0; posture → sitting, command and `sequence_s` cleared; waits `STAND_DOWN_S` | 0; no change |
| `Stretch` | 0; waits `STRETCH_S` | 1 |

- **Odometry.** An accepted `Move(vx, vy, vyaw)` (return 0) stores the command in the state file and `StopMove()` clears it, so a command stays set until a `StopMove` arrives, as assumed for the robot ([robot.md](robot.md#working-assumptions)). The service's motion clock is `SimRobot.wait(seconds, abort)`: it waits the scaled time or until the primitive is aborted, and while a command is stored advances the pose by the **unscaled** seconds waited, integrating the body-frame velocity exactly along the arc. The pose moves only while the service's motion loop waits; a command left set by a dead or hung service shows in `velocity` but moves no pose. Body frame as on the Go2: +vx forward, +vy left, +vyaw counter-clockwise (left).
- **Start ramp as dead time.** A `Move` sequence starts when a command is set from none and ends at `StopMove` (also at `StandDown` and `stub_state.reset`); a `Move` while a command is set continues it. `sequence_s` in the state file is the unscaled time waited in the current sequence. The linear axes (vx, vy) move only once `sequence_s` passes `LINEAR_DEAD_S`, the yaw axis once it passes `YAW_DEAD_S`; a wait that crosses a dead time integrates each part with the axes running in it. The dead times are the robot's calibrated start ramp, `services/robot/ramp.py` (1.1 s linear, 0.2 s yaw), the same values the skills add as `LEAD_S`, so `walk` and turn's open-loop fallback cover the commanded distance or angle on the stub (the open-loop turn to the nearest command period). `velocity` and `yaw_speed` still report the command during the dead time. The stub does not model the coast or collisions: a closed-loop turn stops at the first command period whose yaw change reaches the angle minus `YAW_STOP_MARGIN_RAD`: between 3° short and 0.1 rad (5.7°) minus 3° past at `YAW_RATE_RPS` (`turn 90°` stops after 18 periods at 91.7°), where the robot stops about the margin short and then coasts ([robot.md](robot.md#motion)). The sim backend's service publishes a state after every motion-clock wait as well as every `SIM_PERIOD_S`, so a yaw target reads the pose of the tick just run at any time scale.
- **Objects.** `GO2_STUB_OBJECTS` is a JSON object: each key is a COCO class name and each value is `{"x": number, "y": number}` in metres in the world frame, with an optional `"height_m": number > 0`; no other keys. Without `height_m` the class's entry in `DEFAULT_HEIGHTS_M` is used (bottle 0.25, cup 0.10, chair 0.90, person 1.70); a class without one is an error naming the class. `contract.stub.parse_objects(data)` holds these rules and raises `ValueError`; `contract.stub.objects()` reads `GO2_STUB_OBJECTS`. One object per class.
- `sim.sample_state()` is the stub's state message. Skills see it through the [robot service](#robot-service), whose sim source calls it every `SIM_PERIOD_S`; the utilities call it in their own process. It reports every field of the real sample except `range_obstacle_raw`, with the robot's values for the posture, so `derive_posture(body_height, mode)` gives the stub's posture ([robot.md](robot.md#state-sampling)): `body_height` per posture (`BODY_HEIGHT_*_M`), `position` = [x, y, `body_height`], `imu_rpy` = [0, 0, yaw], `velocity` (world frame) and `yaw_speed` from the stored command, so zero at rest, `mode` `MODE_STANDING` (0, measured) or `MODE_SITTING` (5, *unverified*), `gait_type` 0, `error_code` 100 and `foot_force` [0, 0, 0, 0], the values every standing sample on the robot carried. A [robot fault](#robot-faults) changes these fields. `obstacle_m` is ray-cast from the body centre in the body's front, back, left and right directions against the objects in `GO2_STUB_OBJECTS`, each a disc of radius `OBSTACLE_RADIUS_M` (0.15 m, *tunable*); the distance is to the disc's edge, and a direction with no hit within `OBSTACLE_MAX_M` (5 m, *tunable*) is `null`. Stub robots can walk through objects: with the body centre inside a disc, every direction reports 0.0. The real mapping never yields 0.0, because it treats 0 as unknown. The stub models no walls or room bounds, so an empty world gives all `null`. The stub invents no raw array, because the encoding the firmware uses is unknown ([robot.md](robot.md#state-sampling)).
- All stub waits are multiplied by `stub.time_scale` (`contract.backend.time_scale()`): skills wait through `backend.sleep()`, the service's motion loop through `SimRobot.wait`. Skills never call `time.sleep` themselves.
- The stub is reset to `stub.initial_posture` at the origin at startup and by `go2 --reset-stub`, not between tasks ([running.md](../../../docs/running.md)). The dispatcher does this with `stub.reset_stub(posture, path)`, its only access to stub state; start-up posture on either backend comes from the `read_state` utility.

### Fault injection

Faults exercise every failure path with real processes. They apply to the stub backend only (`stub.faults` must be empty with `robot.backend = "real"`; that is a config error).

Configure them in config:

```toml
[stub]
faults = [ { step = 2, kind = "hang" } ]
```

or on the command line with `--fault STEP:KIND` (repeatable), which replaces the whole list ([running.md](../../../docs/running.md)).

- `step` counts **dispatched** steps in the task, 1-based, across plans. Rejected steps are not counted. Steps must be unique.
- The `SKILL_FAULTS` kinds `error`, `hang`, `crash` and `garbage` go to the skill process in `GO2_STUB_FAULT`, for that step only, and act there ([skills.md](../../../skills/docs/skills.md)); neither service sees them.
- The `ROBOT_FAULTS` kinds `service_hang`, `service_crash`, `stop_error`, `rejected`, `fallen` and `stuck` go to the robot service in the **fault file**, never on the wire. Before it arms the step's lease, the dispatcher writes `{"kind": "<robot fault>"}` to `contract.faults.fault_file(state_file)`, the stub state file's path with the suffix `.fault.json` (`write_fault`, atomic). At that `arm`, the sim backend's arm hook first clears the service's `FaultySportClient` (the previous lease's sticky faults and any fault not fired), so ending a lease still in use sends a `StopMove` that is not faulted; once the old lease has ended, it takes the file (`take_fault`: read and remove; missing means no fault) and arms the wrapper with the kind. A file with bad JSON or no robot fault is removed and the `arm` is refused with `bad_request` (`BadFaultFile`). The sim backend removes the file at service start and `stub_state.reset` (`go2 --reset-stub`) removes it, so a stale fault never reaches a later step.
- The wrapper fires the armed fault once, at the lease's first sport call: after its first `Move` if that returned 0 (mid-walk, the sim robot has a velocity command), or before its first action. A first `Move` that fails consumes the fault unfired. `stop_error` and `rejected` then stay until the next `arm`. A step that sends no motion (`detect_object`) never fires its fault; the next `arm` drops it.
- The utilities (`stop_move`, `read_state`) use a bare `SimRobot` and never read the fault file, so the fallback stop always works. The real backend never reads the fault file and never imports the fault code (`backends/faults.py`, `contract.faults`); a test checks the import chain ([safety.md](../../../docs/safety.md#supervised-operation-rules)).
- The fault kinds are `contract.faults.FaultKind` (`FAULT_KINDS`), split into `SKILL_FAULTS` (applied in the skill process) and `ROBOT_FAULTS` (applied by the robot service or the sim robot) ([contract.md](../../../contract/docs/contract.md#the-package)); the dispatcher's `stub.faults[].kind` config type is that same `Literal`, as `stub.initial_posture` is `contract.stub.StubPosture`. The `stub.time_scale`, `stub.initial_posture` and `stub.state_file` config defaults are `contract.backend.DEFAULT_TIME_SCALE`, `contract.stub.DEFAULT_POSTURE` and `contract.stub.DEFAULT_STATE_FILE`, the same values the stub uses when its env is unset.

| Kind | Where it acts | Observable result | Step outcome |
|---|---|---|---|
| `error` | skill process | the call returns 99 (`sdk_error`, e.g. `Move returned 99`); the detector raises a camera error (`camera_unavailable`) | `error` |
| `hang` | skill process | sleeps forever (not scaled) | `timeout` (killed, then `StopMove`) |
| `crash` | skill process | exits with code 139, no output | `malformed` |
| `garbage` | skill process | prints `not json` and exits 0 | `malformed` |
| `service_hang` | robot service, the motion-loop thread (`apply_process_fault`) | the service stops itself with `SIGSTOP` mid-walk: sockets stay open, nothing answers, the sim command stays set | `error` (`robot_unavailable`, no reply within the skill's reply wait) unless the dispatcher detects the hung service first (no `ping` or `stop_sent` reply) |
| `service_crash` | robot service, the motion-loop thread (`apply_process_fault`) | the service exits with code 139 (`CRASH_EXIT_CODE`) mid-walk, the sim command stays set | `error` (`robot_unavailable`, connection lost); the dispatcher sees EOF on its control connection |
| `stop_error` | `FaultySportClient.StopMove` | every `StopMove` of the service returns 99 (`STUB_ERR_INJECTED`) until the next `arm`, without reaching the sim robot, so the sim command stays set | `error` (`sdk_error`, `StopMove returned 99`, for `walk` and `turn`; `ok` for `sit` and `stretch`); the `disarm` reply carries `stop_failed` with `ret` 99 |
| `rejected` | `FaultySportClient.Move` and the actions | every `Move` returns 3102 (`SDK_ERR_CLIENT_SEND`) and every action 3104 (`SDK_ERR_API_TIMEOUT`) until the next `arm`, without reaching the sim robot; `StopMove` still works | `error` (`sdk_error`, `Move returned 3102` after one period of motion, or `StandDown returned 3104`) |
| `fallen` | the sim robot (`SimRobot.inject`), state file `condition` | falls on its side mid-walk (or before the action) and stays fallen until `stub_state.reset` | `ok`: every SDK call returns 0; only the state shows the fall |
| `stuck` | the sim robot (`SimRobot.inject`), state file `condition` | holds its pose for the rest of the walk's `Move` sequence; nothing without a running command | `ok`: the walk reports its full duration; a closed-loop `turn` runs to its cap; only the state shows no motion |

For one process run by hand, set `GO2_STUB_FAULT=<kind>` for a skill fault; for a robot fault, call `contract.faults.write_fault(state_file, kind)` before the `arm` (as `tests/integration/robot.py` does).

#### Robot faults

`fallen`, `stuck` and `rejected` give the dispatcher's [fault detection](../../../dispatcher/docs/loop-and-context.md#verification) the signals of a robot that fell, did not move, or did not take a command, in the fields and value ranges of the real sample. The robot's signature of each is *unverified*; the values are assumptions (*tunable*, to be confirmed on the robot, [robot.md](robot.md#open-robot-side-questions)).

- **`fallen`** sets `condition` `fallen` and clears the command. Until `stub_state.reset` (`go2 --reset-stub`), the sim robot accepts every call with 0 and does nothing: `Move` is sent without a reply on the robot, so a fallen robot cannot reject it with a code, and the actions are assumed to be accepted too. The sample reports `imu_rpy` roll `FALLEN_ROLL_RAD` (π/2, on its side; the robot's standing samples stay within ±0.14 rad roll and pitch), `body_height` `FALLEN_BODY_HEIGHT_M` (0.10 m), `mode` `MODE_FALLEN` (7, damping in Unitree's sport mode list), zero `velocity` and `yaw_speed`, and the posture the posture rule gives for these, `sitting`: the v1 rule calls a fallen robot sitting, which is why fault detection reads roll and pitch.
- **`stuck`** sets `condition` `stuck` while a command is set (with none, it does nothing; so it never acts on `sit` or `stretch`). `Move` keeps returning 0 and the command stays set, but the motion clock moves no pose, and the sample reports zero `velocity` and `yaw_speed` (assumed: the robot's own estimate shows no motion). The condition ends with the `Move` sequence (`StopMove`, `StandDown`, `stub_state.reset`). Foot force cannot show a stuck robot: `rt/sportmodestate` reports `foot_force` as zeros on the robot, so the stub does too.
- **`rejected`** keeps the sim robot as it is and fails the calls in the wrapper, like `stop_error`. The codes are the SDK's (`unitree_sdk2py/rpc/internal.py`): `Move` is sent without waiting for a reply, so the only non-zero code it can return is a failed send, `SDK_ERR_CLIENT_SEND` (3102); an action waits for a reply, and `SDK_ERR_API_TIMEOUT` (3104) is the failure seen on the robot ([robot.md](robot.md#known-issues)). A refusal by the robot's sport server would return a server code, which is undocumented. The skill turns the code into `sdk_error` exactly as on the robot, through the same service reply.

## Design decisions

- **One robot backend interface, selected once per process.** The real-or-sim choice is made in one place, `backends.load()`, and every user of the robot (the service's state source, sport client and motion clock, the utilities' DDS init, client, sample and settle wait) calls the object it returns, so no code branches on the backend name and the real backend's call chain contains no sim code (a test checks that loading it imports neither the SDK nor the sim). Rejected: a name check at each use (four in the utilities and three in the service, each a place where a stub path could reach the real robot or the reverse); a plug-in registry by entry point (left out until a third backend exists).

- **Skills read state through one long-running robot service; it is the only long-lived DDS subscriber of the sport state.** In a fresh process the subscription, DDS discovery and the first message took about 170–190 ms of every step on the robot, and a fresh process could not create a DDS domain at all while the Ethernet link was unstable; a participant that is already up avoids both, and a read is a socket round trip to a message already in memory. It also gives the dispatcher a fresh state at any time and a continuous stream for logging. The DDS callback only stores the latest message, so readers never wait on the robot and the callback never waits on a reader. Rejected: a shared-memory state buffer (a sub-millisecond gain for real complexity); ZeroMQ or HTTP (a dependency each, no gain over `multiprocessing.connection`); a separate state process beside the motion owner (two lifecycles and two participants without a measured need).
- **The service runs motion primitives; skills keep the policy and send one primitive per motion.** The 10 Hz `Move` loop runs next to the sport client, so its timing does not depend on socket round trips or a skill process being scheduled, and a later obstacle guard or closed-loop motion can act inside the loop where the state is. Skills keep speeds, lead times, direction maps and durations, so the `SKILL.md` sync test and the motion budget still read them in one place. Rejected: skills streaming `Move` through the service as a proxy (one round trip per command, and a stalled skill would stall the command stream without the service knowing why).
- **One sport client in the service sends both motion and every stop.** SDK replies are matched per request id (`unitree_sdk2py/rpc/client_stub.py`) and `Move` never waits for a reply, so a `stop` from a handler thread is never queued behind a running primitive or an action waiting for its reply. Rejected: a separate stop client (a second client with nothing to separate).
- **An action is committed under the lease lock but called outside it, with a trailing `StopMove` if the lease ends during the call.** No action starts after a stop has taken the lock, and a stop never waits on an action's reply (up to `SPORT_CLIENT_TIMEOUT_S`, 5 s). A stop that lands between the commit and the request reaching the robot can still arrive first; the trailing `StopMove` then follows the action. Rejected: holding the lock across the call (a stop would queue behind the reply, which the one-client decision above rules out).
- **Motion needs a lease armed by the dispatcher, bound to one connection, with a deadline the service enforces.** "Stationary during LLM calls" and "only the current step moves" are then enforced where the sport client is, not only in the dispatcher: a stray or late skill, a second client, or a dispatcher bug cannot move the robot. Binding the lease to the skill's connection turns the skill's death into EOF, which the service answers with `StopMove` even if the dispatcher's `stop` is lost. Rejected: trusting the dispatcher's sequencing alone (one bug from motion during planning); a lease without a deadline (a dispatcher that hangs while a step runs would leave it open).
- **Every loss path ends in an explicit `StopMove`: lease connection EOF, deadline, control connection EOF, orphan watchdog, `SIGTERM`, a failed `Move`, an SDK exception.** The robot is assumed to keep its last velocity until `StopMove` ([robot.md](robot.md#working-assumptions)); no path relies on the robot stopping by itself when commands stop arriving.
- **The service reports its own failed `StopMove` once per step, in the `disarm` reply, as the lease's latest `StopMove` if it failed.** The dispatcher sends `disarm` after every step that was not stopped by its own `stop`, and the `stop_sent` reply already carries that stop's code, so the two replies cover every `StopMove` of a step. Every service-sent `StopMove` ends in this one record: the one ending a `move`, a lease deadline, the lease connection's EOF (the skill may be dead and cannot report it) and the `disarm` itself. `disarm` waits for a `StopMove` already decided on another thread, so a skill that died just before cannot race the reply. The latest one counts because a later `StopMove` that returns 0 stops the robot: after a `move` whose `StopMove` failed, the lease's end sends another. Rejected: a skill error code or response field for the `move` stop (a skill response change and a schema bump, and it misses the deadline and the EOF paths, where no skill reports); the first failure since `arm` (it would end a task whose robot a later `StopMove` stopped); a separate status request (one more round trip after every step, and a race with a stop still running).
- **The fresh-process `stop_move` utility stays as the permanent fallback stop.** A hung or dead service cannot send a stop, and its sport client is gone or stuck with it; `stop_move` creates its own DDS participant and sport client and works when nothing else does. `read_state` stays as the diagnosis read that bypasses the service. Both reach the robot through the [backend object](#robot-backends), which no skill may import.
- **No staleness watchdog that stops the robot on old state.** If the link is down a `StopMove` does not arrive either, and failed calls already surface the loss. A guard that reads state checks the age of what it reads. Rejected: stopping on old state while moving.
- **A skill's state sample is the first message after the request (`min_seq` = latest `seq` + 1), waiting at most `STATE_WAIT_S`.** This is the freshness rule of an in-process subscription, so samples taken through the service stay comparable with samples taken in the skill process; the latest message alone could predate the skill's own action by up to one message period. Each sample carries `seq` and `age_ms`, so its freshness is visible in the log. The dispatcher may read without `min_seq` where the latest message is fresh enough.
- **The robot service's socket is at a fixed path in `log.dir`, guarded by a lock file.** One robot owner per log dir, and any other client, such as a telemetry reader, can attach to the running service by path. The `flock` is released by the kernel on any exit, so a killed service never blocks the next start, and the socket file is removed only by a process that holds the lock. Rejected: a socket per dispatcher PID, as the [vision service](../../vision/docs/vision.md#vision-service) uses (nothing else can attach, and two dispatchers could each start a service for the same robot).
- **The service is the only robot path for skills; there is no switch back to per-process DDS.** Two paths would double the code and tests to keep in step; `git revert` is the rollback in development. Rejected: a `robot.io = "process" | "service"` config switch. Kept by design: `stop_move` and `read_state` (above).
- **Every robot service message carries the protocol version, and connections start with `hello`.** The service runs for the whole dispatcher run and other processes attach to it, so a client and a service from different code can meet; the version check turns that into `ProtocolMismatch` instead of misread fields.
- **The SDK reply timeout `SPORT_CLIENT_TIMEOUT_S` (5.0 s) must fit inside the timeout of every process whose call reaches the sport client, so a lost reply gives an error response, not a kill.** A kill leaves no response, no `state_after` and no SDK code for the log, while `sdk_error` keeps all three. On the robot, a 90° `turn` whose `StopMove` reply was lost waited the old 10 s and was killed at its 12.4 s timeout. The move-loop base is derived from the SDK timeout, so the two cannot drift; the constant timeouts of `sit`, `stretch` and `stop_move` are checked by a test. Rejected: 2 s (too tight per operator decision); keeping 10 s, which no move-loop or single-action timeout covered.
- **The stub replaces only the robot: `SimRobot` is the robot service's sport client on the sim backend**, so process start, the service, the lease, timeouts, kills and both stop paths are exercised for real offline. The sim command stays set until `StopMove`, as assumed for the robot, so a test sees a robot left moving. Rejected: a stub sport client inside the skill process (it would bypass the service the real backend uses).
- **The stub models the start ramp as dead time per axis, from the same constants as the skills' lead times.** The robot loses a roughly constant time at the start of each `Move` sequence (1.1 s linear, 0.2 s yaw, [robot.md](robot.md#design-decisions)), and the skills command that much longer; without a ramp the stub overshot `walk` by `LEAD_S` × speed (0.33 m), enough to end inside an object's disc. Dead time is the simplest model that matches the constant-offset calibration exactly: zero displacement for the first part of a sequence, then the commanded velocity. The values live once in `services/robot/ramp.py`, a leaf module that `walk`, `turn` and the sim all import, because `robot` does not import the skill modules and the ramp is a robot fact, not a skill's policy. The progress lives in the state file because the service calls `wait` once per command period. Rejected for now: a linear acceleration ramp (a second parameter the calibration cannot separate yet); stopping at objects (collision modelling, not needed to keep the ramp honest); stub-owned copies of the values (two numbers to keep in sync).
- **The fault kinds, the stub world format and the utilities' process runtime are `contract`'s; `robot` applies them.** The reasons are in [contract.md](../../../contract/docs/contract.md#design-decisions). `robot` keeps what only the robot side does: applying a robot fault, the stub state file and the sim.
- **The dispatcher touches stub state only through `stub.reset_stub(posture, path)`, never the state file or `write_posture`.** The state file layout stays a stub internal, so a richer stub state (such as the robot-fault `condition`) changes `reset` alone, and posture is read the same way on both backends, through `read_state`. Rejected: a stub `read_posture` call in the dispatcher, which needs a backend branch and a second posture path.
- **Fault injection by dispatched step number** (error, hang, crash, garbage) covers each step outcome the executor can produce, with real processes. The service faults (`service_hang`, `service_crash`, `stop_error`) are applied in the robot service mid-walk, so the dispatcher's detection of a hung or dead service and its fallback stop are tested with a robot left moving, and `stop_error` tests the service's report of its failed `StopMove` in the `disarm` reply.
- **Robot faults are conditions of the sim robot; return-code faults stay in the wrapper.** `fallen` and `stuck` live in the stub state file, so every sample (the service's, the utilities') shows them and `fallen` survives a service restart like a real fall; `rejected` and `stop_error` fail calls in `FaultySportClient`, which never reach the sim robot. The faulted fields keep the real sample's meaning and ranges and the step still reports what the robot would report (mostly `ok`), so the dispatcher's verifier is tested on state alone. `rejected` is kept beside `error`: `error` fails in the skill process with 99 and also covers the camera, `rejected` goes through the service with the SDK's codes and a closing `StopMove`. Rejected: a new posture value `fallen` (`StubPosture` is a subset of the real posture type and the dispatcher's config type); a separate fault mechanism for state faults; inventing a foot-force signal the robot does not report in `rt/sportmodestate`.
- **`skills` and `dispatcher` import four `robot` modules: `protocol`, `client`, `ramp` and, the dispatcher only, `stub`.** They are what a client needs: the messages and limits, the connection, the start ramp the skills add as lead time, and the dispatcher's stub reset. Each needs only the standard library and `contract`, so a skill process and the dispatcher load no backend, no service code and no SDK. Rejected: one flat package where any module may be imported (a skill could reach `backends.real` and DDS through an innocent-looking import).
- **The service's lifecycle constants and `SERVICE_MODULE` are in `protocol.py`.** The dispatcher starts the service with `python -m` and `SERVICE_MODULE`, waits for `READY_LINE` within `STARTUP_TIMEOUT_S`, stops it with `STOP_GRACE_S` and reads `EXIT_LOCKED`, all without importing the service. Rejected: importing `services.robot.service` for them, which reaches the backends from the dispatcher process.
- **The stub state file and DDS init are `services.backend`'s, not `robot`'s.** The stub camera reads the state file and the real detector needs the one DDS init per process; the reasons and rejected alternatives are in [backend.md](../../backend/docs/backend.md#design-decisions).
- **The stub reset is its own client-surface module, `services/robot/stub.py`, not part of `client`.** Skills import `client`, and the stub world must stay off a skill process's import graph; `stub` imports `services.backend.stub_state` and only the dispatcher imports `stub`. Rejected: `reset_stub` in `client` (even imported lazily, the static chain puts the stub world on the skills' import graph); the dispatcher calling `services.backend.stub_state` directly, which puts a backend-side module on the dispatcher's import graph.
- **Robot faults are a sim feature: a wrapper the sim backend builds, armed from a sim-only fault file; `Motion` and the wire know nothing of them.** The real backend then contains no fault code at all, and the protocol is identical on both backends, so nothing a stub run exercises differs on the wire from a robot run. The wrapper keeps the firing points the faults had inside `Motion` (after the first accepted `Move`, before the first action, from the motion-loop thread), and the arm hook has two steps around ending the old lease: clearing before it, so the re-arm's `StopMove` is never failed by the previous step's `stop_error`, and arming after it, so the new fault cannot fire on the old primitive. Rejected: one hook after the old lease ends (the re-arm's `StopMove` would fail under the old `stop_error`, and the failure would carry into the new lease's `disarm`); one hook before (the new fault could fire on the old primitive's next `Move`). Skill faults stay in the skill process, where they act. Rejected: a `fault` field on `move` and `action` (the old design: the skill forwarded a stub fault through the protocol, and `Motion` branched on whether its client was a `SimRobot`); a `fault` field on `arm` (still on the wire, and the real service would have to parse and refuse it); the fault in the stub state file (the dispatcher would write the sim's state, and every sampler and the vision stub camera would read a field meant for one arm); a sim-only control op (a protocol message that exists on one backend only).
- **Removing `fault` from `move` and `action` keeps `PROTOCOL_VERSION` at 1.** The field was optional and stub-only; every message valid now was valid before with the same meaning, and the service ignores fields it does not know, so an old skill's `fault` is ignored and only means no fault on the stub. The dispatcher, the skills and the service ship from one checkout, and the dispatcher starts the service it talks to. Rejected: a bump, which would turn a harmless leftover field into a refused connection without protecting anything on the robot.
